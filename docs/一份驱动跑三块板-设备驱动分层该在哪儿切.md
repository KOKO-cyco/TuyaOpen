# 一份驱动跑三块板：设备驱动分层该在哪儿切

写给需要把同一个外设适配到多块板子的嵌入式同学。文中案例是 TuyaOpen 里的 V4L2 摄像头驱动，但要讲的不是摄像头，是**驱动分层的切口该开在哪里、注册表该长什么样、以及三个几乎人人都会踩的坑**。换成 SPI 屏、I2C 传感器、音频 codec，结论一样成立。

## 一、先看症状：你的驱动是不是被复制了三份

一个很常见的目录长相：

```
boards/LINUX/Raspberry_Pi/tdd_camera_v4l2.c     # 640 行
boards/LINUX/TaishanPi_3/tdd_camera_v4l2.c      # 640 行，改了 3 行
boards/LINUX/DshanPi_A1/tdd_camera_v4l2.c       # 640 行，又改了 3 行
```

三块板子都跑 Linux，都用标准 V4L2 接口，都是 `open` → `VIDIOC_S_FMT` → `VIDIOC_STREAMON` → `dequeue/queue` 这套流程。真正不同的只有一个字符串：`/dev/video0` 还是 `/dev/video11`。

但代码是复制的。于是修一个 dequeue 超时的 bug，要在三个文件里改三次；第三次总会漏掉一个。加一个硬件编码分支，三份都要跟。这个目录只会越来越糟，因为每加一块板子，复制成本是零，而收敛成本是线性增长的。

判断标准很朴素：**如果两份代码的差异可以用几个参数表达，那它们就不该是两份代码。**

摄像头这个例子里，差异表达出来是这样的：

```c
/* boards/LINUX/TaishanPi_3/board_com_api.c */
tdd_camera_v4l2_register("camera_v4l2", "/dev/video11");
```

差异只剩下调用参数。那实现自然就该挪到共享位置：

```c
/**
 * @note Lives in boards/LINUX/common/camera so every Linux board links the
 *       same implementation. Each board pulls it in from its CMakeLists when
 *       CONFIG_ENABLE_CAMERA_V4L2 is set, and passes its own device node to
 *       tdd_camera_v4l2_register().
 */
```

各板的 CMakeLists 按需引入，板级代码只负责"我这块板的摄像头挂在哪个节点上"。600 行实现回到一份。

## 二、三层切口：TDL / TDD / TKL 各管什么

分层这件事，难的不是分几层，是**每层的边界用什么规则划**。TuyaOpen 的外设栈分三层，规则可以直接借用：

| 层 | 全称 | 回答的问题 | 谁会改它 |
|---|---|---|---|
| TDL | Tuya Device Layer | 应用要什么（打开一路 1080p H264） | SDK 维护者，很少改 |
| TDD | Tuya Device Driver | 这类设备怎么驱动（V4L2 怎么取流） | 加新品类外设时改 |
| TKL | Tuya Kernel Layer | 这个平台的内核接口长什么样（ioctl / MPP） | 移植到新芯片时改 |

关键在于**每层只对上层暴露"能力"，不暴露"实现"**。

应用层拿到的是这样一个描述：

```c
typedef struct {
    TDL_CAMERA_TYPE_E  type;
    uint16_t           max_fps;
    uint32_t           max_width;
    uint32_t           max_height;
    TDL_CAMERA_FMT_E   supported_fmts; /* 位掩码：YUV422 | JPEG | H264 */
    TUYA_YUV422_ORDER_E yuv_order;     /* 0=UYVY, 1=YUYV */
} TDD_CAMERA_DEV_INFO_T;
```

注意 `supported_fmts` 是位掩码而不是单值，`yuv_order` 是显式字段而不是"大家都知道是 UYVY"。这两个设计决定了上层不需要知道底下是 UVC 摄像头还是 SoC ISP 流水线——它只需要问"你能给我什么格式"。

## 三、注册表模型：函数指针表 + 可选能力

驱动向上注册的动作，一共就三个东西：一个名字、一个私有句柄、一张函数表。

```c
OPERATE_RET tdl_camera_device_register(char *name,
                                       TDD_CAMERA_DEV_HANDLE_T tdd_hdl,
                                       TDD_CAMERA_INTFS_T *intfs,
                                       TDD_CAMERA_DEV_INFO_T *dev_info);
```

`tdd_hdl` 是 `void *`，指向驱动自己的设备结构体，TDL 层原样传回，不解释内容。这是 C 里做面向对象最省事的方式：**上层拿着不透明句柄调函数表，实现细节全在句柄背后。**

函数表本身有个值得学的细节：

```c
typedef struct {
    OPERATE_RET (*open )(TDD_CAMERA_DEV_HANDLE_T device, TDD_CAMERA_OPEN_CFG_T *cfg);
    OPERATE_RET (*close)(TDD_CAMERA_DEV_HANDLE_T device);
    /**
     * Optional, and only meaningful where the driver owns a hardware encoder.
     * ... Leave NULL and the camera simply keeps the settings it was opened with.
     */
    OPERATE_RET (*request_i_frame)(TDD_CAMERA_DEV_HANDLE_T device);
    OPERATE_RET (*set_bitrate)(TDD_CAMERA_DEV_HANDLE_T device, uint32_t kbps);
} TDD_CAMERA_INTFS_T;
```

`open`/`close` 是必选，后两个是可选。**可选接口的正确表达是留 NULL，不是写个空函数返回 OK。**

差别在哪儿？上层是这样用的：视频流卡住了，需要一个关键帧让对端重新起解——于是调 `request_i_frame`。如果驱动填了个 `return OPRT_OK` 的空实现，上层收到成功，安心等待关键帧，然后永远等不到。如果留 NULL（或者返回 `OPRT_NOT_SUPPORTED`），上层立刻知道这条路走不通，可以退回到"重开一路流"这种更粗暴但有效的办法。

这条推广开来是：**"假装成功"比"明确失败"危害大得多。** 后面第五节还会撞到同一个问题的另一个版本。

## 四、能力要探测出来，不能宣告出来

这是我认为最值钱的一条。

驱动注册的时候要填 `supported_fmts`。最省事的写法是照着手册填死：

```c
dev_info.supported_fmts = TDL_CAMERA_FMT_YUV422 | TDL_CAMERA_FMT_JPEG;
```

问题是，同一份 V4L2 驱动面对的硬件差得很远：

- USB 摄像头（UVC）：给 YUYV 和 MJPEG，没有 NV12
- Rockchip ISP 流水线（rkisp/rkvpss）：给 UYVY 和 NV12，**从来不给 YUYV**

宣告了不存在的格式，上层就会去开一个开不起来的流，失败点被推迟到运行时，而且报错信息落在很深的地方。

正确做法是注册时先问设备：

```c
/* Ask the node what it has before advertising anything: a UVC webcam and a
 * Rockchip ISP pipeline expose disjoint format sets, and the YUV422 byte
 * order has to be declared here, long before open() negotiates a format. */
if (tkl_camera_v4l2_probe(devnode, &dev->pixfmt_mask) != OPRT_OK) {
    PR_WARN("v4l2 probe failed on %s, falling back to open-time negotiation", devnode);
    dev->pixfmt_mask = 0;
}
```

然后**根据探测结果推导能力**，而不是反过来：

```c
if (dev->pixfmt_mask & (YUYV_BIT | UYVY_BIT | MJPEG_BIT)) {
    dev_info.supported_fmts |= TDL_CAMERA_FMT_YUV422; /* MJPEG decodes to YUV422 */
}
if (dev->pixfmt_mask & MJPEG_BIT) {
    dev_info.supported_fmts |= TDL_CAMERA_FMT_JPEG;
}
/* H264 needs both a hardware encoder and a node that can hand it NV12. */
if (dev->pixfmt_mask & NV12_BIT) {
    dev_info.supported_fmts |= TDL_CAMERA_FMT_H264;
}
```

注意 H264 那条：它的成立条件是**两个**——编译期有硬件编码器（`ENABLE_TKL_VENC_MPP`），且运行期这个节点能吐 NV12。少一个都不能宣告。V4L2 采集节点本身从来不产 H264，H264 来自独立的编码器模块，这种"能力由多个条件合成"的情况在嵌入式里非常普遍。

字节序同理。YUV422 有 UYVY 和 YUYV 两种排列，搞反了画面颜色整个偏掉。它必须在注册时就确定，而这时候还没 open、还没协商格式，所以只能靠探测结果推：

```c
/* Native YUYV wins only when the node has no UYVY, matching the order
 * __tdd_camera_v4l2_open() tries. MJPEG decode always yields UYVY. */
dev_info.yuv_order = (!(mask & UYVY_BIT) && (mask & YUYV_BIT)) ? TUYA_YUV422_YUYV
                                                               : TUYA_YUV422_UYVY;
```

这里还有个隐藏约束值得说：**推导规则必须和 open 时的尝试顺序严格一致**。open 里先试 YUYV 再试 UYVY，那注册时的推导就得按同样的优先级来，否则宣告的字节序和实际打开的格式对不上，颜色又错了。这种"两处逻辑必须同步"的地方，注释里写清楚比什么都强。

## 五、别信配置，要测量：帧率这个坑

摄像头以 15fps 还是 30fps 出图，看起来是配置项，`cfg->fps` 传进去就完了。

实际上这个 ISP 流水线**直接拒绝 `VIDIOC_S_PARM`**，也拒绝 `VIDIOC_G_PARM`。它以固定帧率跑，你设不了也读不到。

如果不管这件事，会发生什么？编码器的码率控制是这样算的：

```
每帧比特预算 = 目标码率 / 帧率
```

你告诉它 30fps，实际出 15fps，那么每帧预算按 30 算，但一秒只出 15 帧——**实际码率正好超标到目标的 2 倍**。这个超标倍数就是 `requested / actual`。

超标之后会发生什么，比数字本身更值得记：下游所有的排队、拥塞、重传调优全都白做。链路承载不了源端产出的量，改传输层参数是治不好的。**它看起来像网络问题，根子在采集端。**

代码里的处理分两步。open 时先问一次：

```c
/*
 * Rate control divides the bitrate by the frame rate to get a per-frame bit
 * budget, so it needs the rate the sensor actually delivers. This ISP
 * pipeline rejects VIDIOC_S_PARM outright and runs at a fixed rate; feeding
 * the encoder the requested rate instead overshoots the target bitrate by
 * exactly requested/actual.
 */
if (tkl_camera_v4l2_get_fps(dev->tkl_hdl, &real_fps) != OPRT_OK || real_fps == 0) {
    real_fps = cfg->fps;
}
if (real_fps != cfg->fps) {
    PR_WARN("camera runs at %ufps not the requested %ufps; rate control follows the hardware",
            real_fps, cfg->fps);
}
```

问不出来的话，跑起来实测。取流线程里开一个一秒的滚动窗口，数第二个完整窗口的帧数：

```c
if (!dev->venc_fps_corrected) {
    uint32_t measured = dev->win_frames * 1000 / ms;

    dev->venc_fps_corrected = true;
    if (measured > 0 && measured != dev->fps) {
        PR_WARN("camera measured at %ufps, not the configured %u; correcting rate control",
                measured, dev->fps);
        if (tkl_venc_mpp_set_fps(dev->venc, measured) == OPRT_OK) {
            dev->fps = (uint16_t)measured;
        }
    }
}
```

顺带一个容易漏的连锁反应：**GOP 是用帧数表达的，帧率变了它代表的时间就变了。**

```c
/* GOP is expressed in frames, so scale it with the real rate to keep
 * the interval between I-frames the caller asked for in seconds. */
venc_cfg.gop = (cfg->gop && cfg->fps) ? (cfg->gop * real_fps / cfg->fps) : cfg->gop;
```

调用方想要的是"每 2 秒一个 I 帧"，写下来是 `gop = 60`（按 30fps）。实际 15fps 时，60 帧变成了 4 秒。要保住调用方真正的意图，就得跟着实际帧率缩放。

**参数里凡是"用 A 单位表达 B 意图"的，B 才是契约，A 得跟着环境变。**

## 六、静默重试是排查地狱

最后一个坑，短但值钱。

取流线程的骨架都长这样：dequeue 一帧，处理，还回去，循环。dequeue 失败了怎么办？绝大多数人写的是：

```c
if (rt != OPRT_OK) {
    tal_system_sleep(10);
    continue;
}
```

看起来很稳健，实际上制造了一个最难查的故障形态：**流水线接受了 STREAMON，然后什么都不给。** 从上层看，进程活着，线程在跑，没有任何报错，日志一片安静。跟一个正常但没人拉流的摄像头长得一模一样。

真实的处理应该是让它出声，同时不刷屏：

```c
/* A pipeline that accepts STREAMON and then delivers nothing looks
 * exactly like a healthy idle camera from here, so say so rather
 * than retry in silence. */
if (++dev->dq_fail_run == 1 || dev->dq_fail_run % 500 == 0) {
    PR_WARN("camera delivered no frame for %u tries (dequeue %d); pipeline is armed but idle",
            dev->dq_fail_run, rt);
}
```

三个细节：第一次就报（第一时间有线索），之后按次数降频（不刷屏），恢复时也报一次（知道什么时候好的）：

```c
if (dev->dq_fail_run) {
    PR_INFO("camera recovered after %u empty tries", dev->dq_fail_run);
    dev->dq_fail_run = 0;
}
```

计数器放在 `dev` 里而不是写成 `static`，因为可能有两路流同时在跑，static 会让两路的计数混在一起，降频逻辑按混合值触发，日志就再也对不上号了。

## 七、可以直接抄走的检查清单

把这几条对着自己的驱动过一遍：

**分层**
- [ ] 板级代码里有没有大段的设备驱动实现？差异能不能用参数表达？能就往上提
- [ ] 驱动有没有直接调用某芯片的头文件？跨层调用是下次移植的债

**注册**
- [ ] 私有状态是不是藏在 `void *` 句柄背后，上层不解释内容
- [ ] 可选能力是不是留 NULL，而不是空实现返回 OK
- [ ] 上层能不能只凭 `dev_info` 就决定怎么用这个设备

**能力**
- [ ] `supported_fmts` 这类字段是探测出来的还是照手册填死的
- [ ] 需要多个条件合成的能力（编译期开关 + 运行期探测），是不是都检查了
- [ ] 注册时的推导规则和 open 时的尝试顺序是否一致

**参数**
- [ ] 硬件拒绝设置的参数，有没有读回来或者测出来
- [ ] 有没有"用帧数表达秒数"这类换算，环境变了跟着缩放了吗

**失败**
- [ ] 重试循环里有没有一条能被人看见的日志
- [ ] 首次报 + 降频报 + 恢复报，三个时机齐不齐
- [ ] 统计计数器是不是每设备一份，没有写成 static
