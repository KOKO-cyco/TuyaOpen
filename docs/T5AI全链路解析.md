# 第一章　先建立世界观

## 1.1 这台设备在干什么？

**your_chat_bot** 是一个「能说话的 IoT 玩具/助手」：

1. 你对着麦克风说话。  
2. 设备把声音数字化，经互联网送给涂鸦云。  
3. 云端做语音识别（把声音变成文字）、大模型理解、再合成语音（TTS）。  
4. 设备下载或接收语音流，从喇叭播出来。  
5. 可选：屏幕显示表情、聊天文字；手机 App 也能看对话、改角色、调音量。

要完成这件事，设备必须同时解决：**上电能跑、有内存、有存储、能连 Wi‑Fi、能安全连云、能采音播音、能显示、能被 App 配网**。下面所有章节都是在拆这些能力。

## 1.2 三个身份别搞混

| 名字 | 它是什么 | 你要记住什么 |
|------|----------|--------------|
| **T5AI** | 模组/开发板品牌线 | 硬件载体 |
| **BK7258** | 模组里的主芯片型号 | 真正干活的 SoC |
| **your_chat_bot** | 烧进芯片里的应用程序 | 产品逻辑 |

芯片厂商提供驱动与双核系统；涂鸦 OpenSDK 提供「连云 + AI」框架；your_chat_bot 决定「默认按住说、音量 DP 怎么处理、屏上显示什么」。

## 1.3 软件分层（不记路径，记职责）

从上到下四层，**越往下越靠近硬件，越往上越靠近产品**：

```text
┌─────────────────────────────────────┐
│  应用层 your_chat_bot               │  产品策略：何时说话、DP、UI
├─────────────────────────────────────┤
│  业务服务（云 / AI / 播放器 / 配网） │  通用能力：MQTT、TTS、激活…
├─────────────────────────────────────┤
│  TAL（抽象层）                       │  统一 API：线程、KV、定时器、事件
├─────────────────────────────────────┤
│  TKL + 芯片平台                      │  真正操作 FreeRTOS、Flash、Wi‑Fi
└─────────────────────────────────────┘
```

- **为什么要 TAL？** 换芯片时，应用少改：都调「创建线程」，底下再映射到 FreeRTOS 或 Linux pthread。  
- **你改产品**，多数时间在最上面两层；**你改跑不起来、连不上网**，才往下钻。

## 1.4 几个必须懂的词

| 词 | 白话 |
|----|------|
| **固件** | 烧进 Flash 里、上电就跑的程序镜像 |
| **线程** | 操作系统里「同时推进」的一条执行流，各有自己的栈空间 |
| **栈** | 函数调用、局部变量用的内存；太小会栈溢出死机 |
| **堆** | 动态申请（malloc）的内存；PSRAM 堆很大，SRAM 堆很小 |
| **阻塞 / yield** | 卡住等 I/O vs 主动把控制权交回，让别人也能跑 |
| **回调** | 「事情发生时请调用我写的这个函数」 |
| **事件** | 系统广播「MQTT 连上了」「VAD 开始了」，订阅者各自处理 |
| **KV** | Key-Value，像一个小数据库：用字符串键存一段数据，掉电还在（在 Flash 里） |
| **DP** | Data Point，App 与设备约定的一个「开关/数值/字符串」控制点 |
| **PID** | 产品 ID，涂鸦平台上创建产品时生成，标识「这是哪类产品」 |
| **UUID / AuthKey** | 设备身份证与私钥；量产写入，开发可用测试号 |
| **激活** | 设备第一次用 token 向云换取 devid、密钥等，之后才能 MQTT |
| **配网** | 把家里 Wi‑Fi 的 SSID/密码交给设备的过程 |
| **TLS** | 传输层加密，防窃听；HTTPS、MQTT over TLS 都靠它 |
| **ASR** | 语音→文字（多在云端） |
| **TTS** | 文字→语音（云端合成，设备播放） |
| **VAD** | 检测「有没有人在说话」 |
| **KWS** | 关键词唤醒（如「小智小智」类，视方案） |
| **OTA** | 空中升级：云下发新固件，设备写入 Flash 再重启切换 |

# 第二章　硬件：两颗「脑」、三种「仓库」

## 2.1 为什么有 CP 和 AP？

BK7258 是 **双核**。可以想成公司两个部门：

| | **CP（Co-Processor，协处理核）** | **AP（Application Processor，应用核）** |
|---|----------------------------------|----------------------------------------|
| **主营业务** | **让设备能连上世界**：Wi‑Fi、BLE、射频、底层协议栈、电源协同 | **连上之后干什么**：聊天、UI、云协议、AI、DP |
| **人话** | 网管 + 射频工程师 | 产品经理 + 应用开发 |
| **Flash 里的家** | `0x00022000` 起，约 1088KB 的 CP 固件区 | `0x00132000` 起，约 3808KB 的 AP 固件区 |
| **你的 your_chat_bot** | 不跑在这里 | **跑在这里** |

启动顺序固定：**先 CP，再由 CP 把 AP 拉起来**。  
改对话逻辑、表情、音量 DP → 改 AP 侧应用。  
Wi‑Fi 驱动诡异、射频校准 → 才碰 CP。

## 2.2 SRAM：640KB 片上内存（基址 `0x28000000`）

**SRAM** = 芯片内部、访问快、容量小的内存。

本工程切成大致：

- AP 自旋锁区、AP 通用区（OS、小对象、**必须放片内的线程栈**）  
- CP 通用区  
- 极小的电源管理 / SWAP 区  

**为什么 your_chat_bot 的主线程栈强调片内？**  
有些操作（Flash 映射、部分音频前端）要求当前任务的栈在「cache 关闭时仍合法」的片内区域；栈若在 PSRAM，可能触发断言。所以 **主应用线程用 SRAM 栈，大缓冲用 PSRAM**。

## 2.3 PSRAM：16MB 片外内存（基址 `0x60000000`）

**PSRAM** = 外挂伪静态 RAM，慢一点但大很多。

切分里最重要的是：

- **AP 的 PSRAM 堆（约 8.6MB）**：对话缓冲、JSON、大块音频、很多业务 malloc  
- 显示 / 编码 / 音频的 **slab**（按用途预留的大块）  
- CP 也有一小块 PSRAM 堆  

your_chat_bot 若开启扩展内存：解析 JSON 的库可配置成从 PSRAM 申请，避免吃光 640KB SRAM。

## 2.4 Flash：8MB 非易失仓库（`0x00000000`～`0x00800000`）

掉电不丢。装的是：**启动程序、双核固件、升级包、配置、校准**。

完整物理地图：

| 起始地址 | 大小 | 名字 | 装什么（白话） |
|----------|------|------|----------------|
| `0x00000000` | 68KB | 一阶 Bootloader | 芯片复位后最先跑的「引导员」 |
| `0x00011000` | 68KB | tuyaboot | 涂鸦二阶引导：看要不要用新固件、启动谁 |
| `0x00022000` | 1088KB | CP 应用 | CP 整包固件 |
| `0x00132000` | 3808KB | AP 应用 | **含 your_chat_bot 的 AP 整包** |
| `0x004ea000` | 2940KB | ota | 下载新固件的「暂存货架」 |
| `0x007c9000` | 8KB | ota_mgr | 升级状态、指针等管理信息 |
| `0x007cb000` | 8KB | usr_config | 平台/用户配置 |
| `0x007cd000` | 196KB | tuya_data | 涂鸦业务数据总槽（见下） |
| `0x007fe000` | 4KB | sys_rf | 射频校准表 |
| `0x007ff000` | 4KB | sys_net | 快连等网络工厂数据 |

```text
0x00000000 ████ bootloader
0x00011000 ████ tuyaboot
0x00022000 ████████████ CP
0x00132000 ████████████████████████████ AP ← 聊天应用在这
0x004ea000 ████████████████████ ota 暂存
0x007c9000 ▏ ota_mgr
0x007cb000 ▏ usr_config
0x007cd000 ██ tuya_data
0x007fe000 ▏ rf
0x007ff000 ▏ net
0x00800000 结束
```

### tuya_data 里面再切（逻辑类型）

| 地址 | 大小 | 逻辑名 | 白话 |
|------|------|--------|------|
| `0x7cd000` | 4KB | KV 保护区（可选） | 更敏感的键值 |
| `0x7ce000` | 60KB | USER | 用户自定义区 |
| `0x7dd000` | 64KB | KV 类型映射区 | 传统 KV 类型地址 |
| `0x7ed000` | 64KB | **UF（User File）** | 用户文件区；**OpenSDK 的 KV 实际挂在这里的小文件系统上** |
| `0x7fd000` | 4KB | KV Key | 密钥相关 |

**UF 不是 UVC。** UVC 是 USB 摄像头协议；UF 是 Flash 里一块给「文件式存储」用的区域。  
音量、对话模式、复位计数等，最终都是「某个键 → 一段字节」写在 UF 上的 LittleFS 里。

### 关于 CRC 与「虚拟地址」

部分镜像在 Flash 里按规则插入 CRC，物理占用约 `长度×34/32`。OTA/启动代码里会出现「物理地址 ↔ 虚拟地址」换算。你只要知道：**烧录工具和 boot 用的是物理布局；应用读逻辑区用类型查询接口**，不要自己瞎算偏移去写 ota 大区。

# 第三章　上电：从复位到「应用主线程」

## 3.1 Boot 逐步（精确到地址）

1. **复位向量 → `0x00000000` 一阶 Bootloader**  
   硬件规定的入口。职责：最基本的初始化，跳到下一阶段。

2. **`0x00011000` tuyaboot**  
   - 读 `ota_mgr`（`0x007c9000`）：上次升级成功了吗？要不要切到新镜像？  
   - 决定启动 CP 镜像。

3. **`0x00022000` CP 跑起来**  
   - 初始化芯片平台（时钟、中断、RTOS）。  
   - 初始化连接相关底座。  
   - **投票/拉起 AP 核**。

4. **`0x00132000` AP 跑起来**  
   - 再 init 一遍 AP 侧平台与多媒体服务。  
   - 若 RF 校准丢失，尝试从 OTP 或 `sys_rf` 恢复（否则 Wi‑Fi 可能弱/异常）。  
   - 调用 **`tuya_app_main()`** —— 这是 OpenSDK 应用约定入口。

## 3.2 `tuya_app_main` 做了什么？

在 MCU 上，它 **并不直接跑你的业务循环**，而是：

1. 配置一个线程：名字 **`tuya_app_main`**，栈约 **4KB**，优先级中等，**栈在片内**。  
2. 线程入口里调用 **`user_main()`**。  
3. 若 `user_main` 返回（正常设计是永不返回），再删线程。

**为什么要多包一层线程？**  
平台 `main` 所在上下文不一定适合长时间阻塞；应用云循环要独立栈与调度。

## 3.3 `user_main`：应用人生大纲（每个动作的含义）

下面按 **真实调用顺序** 解释。每个名字后面都是「它到底在干什么」。

### （1）配置 JSON 用哪块堆

若开了扩展内存：告诉 cJSON「以后用 PSRAM 的申请/释放」。  
**含义**：解析云下发的大 JSON 时，别把 640KB SRAM 撑爆。

### （2）`tal_log_init` —— 日志系统

设定日志级别、缓冲区、输出回调（写到串口）。  
之后所有 `PR_INFO` / `PR_ERR` 都从这里出去。  
**小白调试第一技能：看串口。**

### （3）打印版本横幅

工程名、版本、编译日期、OpenSDK 版本、芯片/板型信息。  
方便现场确认「烧的是不是这份固件」。

### （4）`tal_kv_init` —— 键值存储

用种子和密钥初始化（内部会做哈希），在 **UF 区** 挂上 LittleFS。  
之后：`tal_kv_set("某键", 数据)` / `tal_kv_get`。  
**掉电仍在**，用来存：激活信息、音量、对话模式、复位计数等。

### （5）`tal_sw_timer_init` —— 软件定时器

创建后台线程 **`sys_timer`**。  
你可以「N 毫秒后调用我的回调」，不必自己开线程 sleep。  
your_chat_bot 用它周期性打印剩余堆、刷新 Wi‑Fi 图标。

### （6）`tal_workq_init` —— 工作队列

创建 **`wq_system`**、**`wq_highpri`** 等线程。  
含义：把「不能在中断或紧要回调里做的重活」丢进队列，由专门线程慢慢做，避免卡死实时路径。

### （7）`tal_time_service_init` / `tal_cli_init`

时间服务（之后云会同步 Unix 时间）；命令行方便工程调试。

### （8）`tuya_authorize_init` + 读授权

尝试读出 **UUID / AuthKey**。  
失败则用头文件里的占位字符串——**占位不能上生产**，云会拒绝；开发必须换成平台申请的测试号。

### （9）`reset_netconfig_start`

启动「连续重启计数」逻辑，为后面的「重启三次清配网」做准备。

### （10）`tuya_iot_init` —— 云客户端诞生

传入：软件版本、**PID**、uuid、authkey、**事件回调** `user_event_handler_on`、**网络是否通** 的探测函数。

内部重要动作（你要心里有数）：

- 清零客户端结构体，保存配置。  
- **`tuya_tls_init`**：TLS 引擎就绪。  
- 注册中心、证书管理初始化。  
- **端点初始化**：知道云域名/证书从哪来。  
- **尝试从 KV 读激活数据**：读到且 schema 可用 → `is_activated = true`（已经是「家里的老设备」）。  
- OTA 模块、健康监控、升级检查定时器、MQTT 分发初始化。  
- 状态设为 **空闲 IDLE**，等你 `start`。

**还没连网，也还没 MQTT。** 只是把「身份证和工具箱」备好。

### （11）网络栈与 netmgr

- 若工程链了独立 lwIP：初始化 TCP/IP。  
- `netmgr_init(WIFI)`：网络管理器管 Wi‑Fi 连接状态。  
- `netmgr_conn_set(..., BLE | AP 配网)`：声明 **两种配网都开**。

### （12）`board_register_hardware`

按板型注册：麦克风、喇叭使能脚、按键、LED、屏等。  
**应用认「设备名」**，不认裸 GPIO 号。

### （13）`app_chat_bot_init` —— AI 聊天子系统

见第六章。注意：此时 **通常还不能真正连 AI 云会话**，要等 MQTT 连通后的回调。

### （14）`tuya_iot_start`

把状态机从 IDLE 推到 **START**。真正连网/激活/MQTT 在后面的 **yield 循环**里推进。

### （15）关掉 Wi‑Fi 低功耗

对话场景要稳定吞吐，避免省电导致卡顿。

### （16）`reset_netconfig_check`

看复位计数是否到阈值，到了就清配网相关数据。

### （17）死循环 `tuya_iot_yield`

**这是设备「活着」的心跳。**  
每一圈根据当前状态做一点点事：检查网、激活、连 MQTT、收发包。  
**绝不能堵死这个循环太久**，否则云保活、消息都会停。

# 第四章　云状态机：`tuya_iot_yield` 每一态在干什么

把客户端想成自动售货机：每次 yield 看「当前状态」，做一步，设「下一状态」。

## 4.1 状态清单（按人生顺序）

| 状态 | 白话 |
|------|------|
| IDLE | 睡一会，啥也不干 |
| START | 出发：已激活？去检查网络；未激活？去加载/待激活 |
| DATA_LOAD | 确认激活数据；没有则进入等 token |
| TOKEN_PENDING | 等 App 配网给出 token；并发 BIND_START 给应用 |
| NETWORK_CHECK | 调你的 `user_network_check`（看 Wi‑Fi 是否 Link Up） |
| ENDPOINT_GET / UPDATE | 向云问「我该连哪个机房/域名」，更新本地端点 |
| ACTIVATING | 用 token 调 ATOP **激活**，结果写入 KV |
| STARTUP_UPDATE | 激活后刷新配置、准备 MQTT 参数 |
| MQTT_CONNECT_START | `tuya_mqtt_start`，注册 DP/复位/升级等协议回调 |
| MQTT_CONNECTING | 等 TLS+MQTT 握手完成 |
| MQTT_YIELD | **日常态**：收发 MQTT、处理 MATOP |
| MQTT_RECONNECT / NETWORK_RECONNECT | 断线重连路径 |
| RESET / RESTART / STOP / EXIT | 复位清理、重启、停止 |

## 4.2 已激活 vs 未激活两条路

**老设备（KV 里已有激活信息）**  
START → 检查网络 → 拿端点 → 更新启动配置 → 连 MQTT → 长期 YIELD。

**新设备**  
START → DATA_LOAD 发现没激活 → TOKEN_PENDING（配网拿 token）→ 有网后更新端点 → ACTIVATING → 再走上电后半程 → MQTT。

## 4.3 应用事件回调：云在「喊」你

`user_event_handler_on` 里常见事件的含义：

| 事件 | 含义 | your_chat_bot 典型反应 |
|------|------|------------------------|
| BIND_START | 开始绑定/配网流程 | 播「配网」提示音 |
| DIRECT_MQTT_CONNECTED | 直连相关 MQTT 节点就绪 | 可打印绑定二维码 |
| MQTT_CONNECTED | **业务 MQTT 已在线** | 上传音量 DP；UI 显示网络好；**AI 侧订阅者在此初始化 agent** |
| MQTT_DISCONNECT | 掉线 | 日志；UI 可变灰 |
| UPGRADE_NOTIFY | 云要你升级 | 打印 URL/版本；后续 OTA 线程干活 |
| TIMESTAMP_SYNC | 云给了 Unix 时间 | 发布 `app.time.sync` 给需要校时的模块 |
| RESET | 复位类型（本地/远程/清数据） | 按类型清 KV 业务数据 |
| RESET_COMPLETE | 复位流程走完 | **整机软件复位** |
| DP_RECEIVE_OBJ | App 下发对象型 DP | 例如音量 → 调播放器音量并回显 |
| DP_RECEIVE_RAW | 原始 DP | Demo 里打印并回执 |

内部还会通过 **事件总线** 发 `EVENT_MQTT_CONNECTED`，AI 模块订阅的是这个总线事件（和上面枚举配套）。

# 第五章　配网：手机如何把 Wi‑Fi「教」给设备

## 5.1 为什么要配网？

芯片出厂不知道你家路由器密码。必须有一种安全方式把 **SSID、密码、绑定 token** 交给设备。

## 5.2 your_chat_bot 开了两种

1. **BLE 配网**  
   手机经蓝牙把凭证传给设备，设备再去连 Wi‑Fi。体验快，文档强调「快速蓝牙配网」。

2. **AP 配网**  
   设备自己开热点（可带 PIN 码校验），手机连上热点后把家里 Wi‑Fi 信息传下来。会起类似 **`ap_cfg_task`** 的线程专门伺候。

两种可并行注册；实际走哪条由 App 与现场决定。

## 5.3 配网成功之后发生什么？

1. Wi‑Fi STA 关联成功 → `user_network_check` 变 true。  
2. 状态机拿到 **token / region** 等。  
3. **ATOP 激活**（HTTPS + 加密）：用 uuid/authkey/token 换 **devid、seckey、localkey、schema**…  
4. 激活 JSON **写入 KV**。  
5. 用这些密钥去连 **MQTT（TLS）**。  
6. 连上 → 应用层「设备在线」→ AI 才能建会话。

## 5.4 重启三次清配网

- KV 键大致为复位计数。  
- 每次上电早期 `+1`；正常跑一段时间或特定事件清零。  
- 计数 ≥ 3：判定用户故意「狂按复位」，清除配网/激活相关数据，回到未配网。  
- 板说明写「重启 3 次复位」就是这个产品策略。

# 第六章　TLS：为什么聊天也要加密

## 6.1 没有 TLS 会怎样？

中间人可窃听 token、聊天相关流量、甚至伪造云。IoT 必须加密。

## 6.2 在本系统里 TLS 扮演什么？

- `tuya_tls_init`：准备好加密引擎（基于 mbedtls **做会话加密**，不是替代 TCP）。  
- 模式可有：PSK、校验证书、双向证书等。  
- **证书管理**：装 CA、处理过期事件。  
- **MQTT**、**HTTPS（ATOP / TTS 拉流 / OTA 下载）** 都走带 TLS 的传输封装。

## 6.3 和「AI 专用链路」的关系

设备往往有：

- **IoT MQTT**：DP、升级、复位、在线状态。  
- **AI Client**：大模型音视频会话（自己的状态机：Setup → Connect → Hello → Auth → Running）。  

两者都要安全通道；AI Client 在 MQTT 已通、agent 初始化之后，由 **`ai_client` 线程** 推进鉴权直到 Running，才稳定送麦/收 TTS。

# 第七章　AI 聊天子系统（your_chat_bot 的心脏）

## 7.1 `app_chat_bot_init` 逐步

1. **`ai_chat_init`**  
   - 注册对话模式插件（按住 / 单击 / 唤醒 / 自由…视编译开关）。  
   - 读 KV：上次音量、模式；没有则用默认（默认模式 HOLD、音量 70）。  
   - 注册用户事件总入口。  
   - **订阅 MQTT 连通事件**：连通后才 `ai_agent_init`。  
   - 初始化 UI（若开）。  
   - 初始化麦克风路径、播放器、KWS；订阅 VAD。  
   - 创建线程 **`ai_chat_mode`**：死循环调用模式状态机，sleep 20ms。  

2. 注册 UI 动作、可选视频/MCP/图片。  

3. 开两个周期定时器：打堆；刷网络图标。

## 7.2 对话模式是什么？

模式决定 **「什么时候开始送麦、什么时候停」**：

- **HOLD（按住说）**：按下说话，松开结束。  
- **单击一轮**：点一下说一句。  
- **唤醒**：先 KWS，再进入收听。  
- **自由说**：更接近连续对话。  

双击按键：停止播放 → 通知云 **CHAT_BREAK（打断）** → 切下一模式 → 写 KV → 播提示音。

## 7.3 上行：你的声音怎么变成「云能懂的流」

```text
麦克风硬件
  → 板级音频驱动（采样率/声道与 agent 配置对齐，常见 16kHz）
  → 线程 record_task：取音、做 VAD
  → 按切片（如 80ms）回调到 ai_chat
  → 若 agent 已初始化：带时间戳调用「音频输入」API
  → ai_agent_input 线程打包
  → AI Client（Running）加密送出
  → 云端 ASR → 大模型 → 生成回复
```

细节：

- **VAD 手动/自动**：模式层根据 VAD 起止决定 `ai_mode_vad_change`。  
- **AEC（回声消除）**：开了可在播 TTS 时仍送麦（打断更自然）；没开则播报时往往不送麦，防自激。  
- **KWS**：本地唤醒，不替代云端 ASR。

## 7.4 下行：云的「话」怎么从喇叭出来

云有两种常见下发：

### A. 流式 TTS（会话中）

agent 事件回调：

- **START + 音频包类型**：`ai_audio_play_tts_stream(START, …)` 打开前景播放。  
- 中间 **媒体数据回调**：把编码帧塞进播放器。  
- **END**：`tts_stream(STOP)` 收尾。  
- **CHAT_BREAK**：立刻停前景播放，并通知 UI「对话打断」。

### B. URL 型 TTS（技能 / cloudevent）

云下发 JSON：`playTts` / `alert`，内含：

- TTS 的 **HTTPS URL**、格式、GET/POST、可选 body  
- 可选背景乐 URL  

设备解析后 `ai_audio_play_tts_url` → 播放器去拉流（再次 TLS）→ 解码 → 喇叭。

### 播放器内部结构（要懂「前景/背景」）

`ai_audio_player_init`：

- 初始化播放服务（16kHz / 16bit / 单声道等）。  
- **前景播放器 + 短播放列表**：提示音、会话 TTS。  
- **背景播放器 + 长播放列表**：音乐/故事等。  
- 订阅播放状态事件，转成「暂停/继续」类用户事件。

线程 **`ai_player`** 整天：取播放任务、下载或取流、解码、往 DAC/喇叭送 PCM。

## 7.5 `ai_agent_init` 做了什么？

在 **MQTT 已连接** 后：

1. 填音频属性：编码（Opus/Speex/PCM）、采样率、声道、位深（从板级音频信息读）。  
2. 注册输出回调：告警、文本（给 UI 字幕）、媒体数据、媒体属性、会话事件。  
3. `tuya_ai_agent_init`：拉起 AI 协议栈（含 input/output 线程等）。  
4. 订阅 **AI Client 进入 Running**：再 `crt_session` 建会话。  
5. 可选监控线程。

之后麦克风数据才真正有「云会话」可去。

## 7.6 AI Client 状态机（另一台小售货机）

线程 **`ai_client`** 循环：

| 状态 | 含义 |
|------|------|
| IDLE | 空闲 |
| SETUP | 准备连接参数 |
| CONNECT | 建连 |
| CLIENT_HELLO | 协议问候 |
| AUTH_REQ / AUTH_RESP | 鉴权请求与应答 |
| RUNNING | **可收发业务数据**；开 ping 保活 |
| 出错 | 按策略退回 SETUP/IDLE |

**`ai_biz_thread`**：业务侧解析、技能分发（TTS URL、音乐、MCP 等）。  
**`ai_agent_input` / `ai_agent_output`**：上行组装、下行拆给播放器/UI。

## 7.7 文本与技能

- 云回的 **文本** → text 回调 → UI 显示聊天气泡。  
- **技能**（音乐、云事件、MCP 工具）：改音量、改模式、播列表等。  
- your_chat_bot 还可把「生成图片」类事件交给打印机模块（若编译进去）。

## 7.8 显示子系统

若开显示：

- **`ai_ui` / `ai_ui_action`**：UI 任务与动作队列（表情、网络图标、通知条）。  
- 应用侧可能还有 **`app_ui_msg`**：LVGL/微信风/聊天风界面消息泵。  
- 初始化时先显示「初始化中」、中性表情；网络定时器刷新强弱（T5 上读 RSSI 可能规避崩溃，用简化逻辑）。

# 第八章　线程百科：谁全天在干什么

把设备想成车间，每个线程是一名工人。

## 8.1 一上电就在的

| 工人名 | 全天工作 |
|--------|----------|
| RTOS 空闲/系统 | 调度、滴答 |
| **sys_timer** | 到点执行软件定时器回调 |
| **wq_system / wq_highpri** | 消化投递来的「延后重活」 |
| **tuya_app_main** | 跑 `user_main`，核心是 **不停 yield 云状态机** |

## 8.2 配网 / 云相关（按需出现）

| 工人名 | 全天工作 |
|--------|----------|
| **ap_cfg_task** | AP 热点配网会话 |
| **mqtt_bind** | 绑定阶段取 token |
| **lan_sock_loop** | 局域网协议循环（若启用） |
| **health_monitor** | 健康检查 |
| **tuya_ota** | 按 URL 下载固件写入 ota 区 |

## 8.3 AI / 音频 / UI

| 工人名 | 全天工作 |
|--------|----------|
| **ai_chat_mode** | 每 20ms 跑对话模式状态机 |
| **record_task** | 录音 + VAD |
| **ai_player** | TTS/提示音/音乐播放流水线 |
| **ai_client** | AI 云连接与鉴权状态机 |
| **ai_biz_thread** | AI 业务/技能处理 |
| **ai_agent_input** | 上行数据送云 |
| **ai_agent_output** | 下行拆给播放与 UI |
| **ai_ui / ai_ui_action** | 界面 |
| **app_ui_msg** | 应用 UI 消息 |
| **ai_mon_log** | 监控日志（若开） |

另外：按键扫描任务、BLE/Wi‑Fi 驱动线程在更底层，日志里名字因平台而异。

## 8.4 优先级直觉

录音、播放、云 yield 不能被慢 UI 长期饿死；模式线程可以较低优先级轮询。具体数字以工程为准，调参前先抓「卡顿时谁占 CPU」。

# 第九章　一次完整人生：从开箱到说完一句话

用时间线把全书串起来。

1. **烧录**：bootloader、tuyaboot、CP、AP（含 your_chat_bot）按地址写入 Flash。  
2. **上电**：`0x0` → tuyaboot → CP@`0x22000` → AP@`0x132000` → `tuya_app_main` 线程 → `user_main`。  
3. **基础设施**：日志、KV(UF)、定时器、工作队列、读授权。  
4. **iot_init**：TLS、证书、端点；若有旧激活则标记已激活。  
5. **netmgr + BLE/AP 配网能力注册**；板级麦喇叭按键屏注册；`app_chat_bot_init`（AI 待命）。  
6. **iot_start + yield 循环**：  
   - 新机：配网 → token → 激活写入 KV → MQTT(TLS)。  
   - 老机：连路由 → MQTT。  
7. **MQTT_CONNECTED**：上传音量；**ai_agent_init**；AI Client 走到 Running。  
8. **用户按住说话**：模式层开送麦 → record_task → agent_input → 云 ASR/LLM。  
9. **云回 TTS**：流式或 URL → ai_player → 喇叭；文本上屏；表情变化。  
10. **用户双击**：打断、切换模式、提示音。  
11. **App 改音量 DP**：回调设音量并上报。  
12. **云推升级**：OTA 线程写入 `0x004ea000`，重启后 tuyaboot 看 `ota_mgr` 切换新 AP/CP。

# 第十章　DP、OTA、时间、安全、低功耗

## 10.1 DP（以音量为例）

- App 下发 dpid=3 数值 → `audio_dp_obj_proc` → `ai_chat_set_volume`。  
- 设备可 `tuya_iot_dp_obj_report` 回传，保持 App 与设备一致。  
- MQTT 首次连接主动上报一次当前音量。

## 10.2 OTA

- 事件带上版本、大小、MD5、URL。  
- 下载写入 **ota 大区**，管理信息进 **ota_mgr**。  
- 校验通过后重启；tuyaboot 负责切到新镜像。  
- 失败则保留旧 AP/CP，避免变砖（具体策略由 boot 与 ota_mgr 状态决定）。

## 10.3 时间

云下发时间戳 → 应用发 `app.time.sync` → 依赖绝对时间的模块（日志、证书校验、部分媒体）受益。

## 10.4 安全注意

- 不要把 AuthKey 打进日志或提交到公开仓库。  
- TLS 校验不要在生产关闭。  
- 复位清数据要按复位类型处理，避免「假复位」残留绑定。

## 10.5 低功耗

聊天场景关闭 Wi‑Fi LP；真休眠产品要另做唤醒与重连设计，不能照搬玩具 demo。
