# 泰山派3（RK3576）点亮 MIPI-CSI0 上的 OV5695 摄像头

记录一次完整的摄像头 bring-up：从「设备节点全在但一帧也拿不到」到「1920×1080 NV12 正常出图」。

**适用对象**：立创泰山派3（RK3576），出厂 Linux 镜像（内核 6.1.99），MIPI-CSI0 接 OV5695 模块。

**一句话结论**：出厂镜像不支持 CSI 摄像头，需要自建设备树 overlay；而 overlay 里唯一容易写错、也是本次唯一实质卡点的，是 **reset 引脚的极性必须是 ACTIVE_LOW**。

## 一、现象

系统里 V4L2 节点一大堆（video33 到 video72），`media-ctl` 能看到完整的 ISP 和 VPSS 拓扑，但是：

```sh
v4l2-ctl -d /dev/video61 --set-fmt-video=width=1280,height=720,pixelformat=NV12 \
         --stream-mmap --stream-count=10 --stream-to=/tmp/out.yuv
# VIDIOC_STREAMON returned -1 (Broken pipe)
# /tmp/out.yuv 大小为 0
```

设置格式能成功，一启流就 `EPIPE`。

## 二、诊断：从下游倒推到源头

### 2.1 EPIPE 说明上游没有数据

先看 `/dev/video61` 所在的拓扑：

```sh
media-ctl -d /dev/media6 -p
```

结果显示它只是链路尾段：

```
rkisp-vir0-sditf (/dev/v4l-subdev0)  ← ISP 输出接口
        ↓ [ENABLED]  fmt: YUYV8_2X8/800x600
   rkvpss-subdev                      ← VPSS 缩放器
        ↓ [ENABLED]
   rkvpss_scale0 (/dev/video61)
```

**VPSS 只是缩放器，自己不产生像素。** ISP 没出流，它一启流就断管。完整链路应该是：

```
sensor → rkcif（media0/1/2）→ rkisp（media3/4/5）→ sditf → rkvpss（media6/7/8）→ /dev/video6x
```

### 2.2 内核明说没有 sensor

```sh
dmesg | grep -iE "rkcif|rkisp|sensor"
```

```
rkcif-mipi-lvds: rkcif_update_sensor_info: get remote terminal sensor failed!
stream_cif_mipi_id0: update sensor info failed -19
rkisp-vir0: No active sensor
```

`-19` 是 `-ENODEV`。再看 media0 的拓扑，最上游的实体：

```
- entity 58: rockchip-csi2-dphy0 (2 pads, 1 link, 0 routes)
                -> "rockchip-mipi-csi2":0 [ENABLED]
```

**两个 pad 却只有一条链路，而且是「出」的。** 它的 sink pad——sensor 该接进来的地方——空着。

### 2.3 驱动在，节点也在，但型号不对

内核里编进了 11 个 sensor 驱动（含 OV5695）：

```sh
zcat /proc/config.gz | grep -iE "^CONFIG_VIDEO_(OV|IMX|GC|SC)[0-9]"
```

```
CONFIG_VIDEO_GC05A2=y   CONFIG_VIDEO_IMX415=y   CONFIG_VIDEO_OV5695=y  ...
```

设备树里也有摄像头节点：

```
i2c@2ac70000 [okay]: gc05a2@37  imx415@37
i2c@2ac80000 [okay]: gc05a2@37  imx415@37
i2c@2ac90000 [okay]: gc05a2@37  imx415@37
```

**但只有 GC05A2 和 IMX415，都在 I2C 地址 0x37。实际模块是 OV5695，地址 0x36。** 所以每次开机这两个驱动都会尝试 probe 并全部失败：

```
gc05a2 4-0037-1: Unexpected sensor id(000000), ret(-6)
imx415 4-0037:   Unexpected sensor id(000000), ret(-5)
```

### 2.4 旁证：模块确实插着

```sh
sudo i2cdetect -y -r 4
# 00:  -- -- -- -- 0c -- -- --
```

`i2c-4`（CSI0 那条总线）上 **0x0c 有设备应答**——典型是模块上的对焦马达驱动。说明排线通、模块部分电路有电，只是 sensor 主芯片没被正确初始化。

**注意**：sensor 本身在 0x36 扫不到是正常的。多数 CMOS sensor 要先有 MCLK 才响应 I2C，而 MCLK 是驱动 probe 时才使能的——没有设备树节点就没有驱动，没有驱动就没有时钟。所以 `i2cdetect` 扫不到 **不能** 用来判断 sensor 好坏。

### 2.5 出厂镜像根本没打算支持 CSI

```sh
ls /boot/overlays/
# overlays.ini  tspi-3m-dsi-c41409463.dtbo  tspi-3m-dsi-c42388916.dtbo
```

只有两个 DSI 屏幕的 overlay，摄像头相关的一个都没有。

## 三、根因

**设备树里没有 OV5695 节点**，所以内核里现成的 OV5695 驱动从未被触发。

## 四、解决：自建设备树 overlay

### 4.1 参数从哪来

不要照抄网上的配置。**同一个 CSI0 接口上已有 GC05A2 节点，它的供电、时钟、GPIO 就是这个接口的真实接法**，直接扒下来当模板最可靠。

先把活动设备树 dump 出来：

```sh
sudo cat /sys/firmware/fdt > board.dtb
```

板子上没有 dtc 也不要紧，DTB 格式简单，可以自己解析（本次用了一个 80 行的 Python 解析器，把 phandle 反查成节点路径）。得到 CSI0 的完整参数：

- **I2C 总线**：`i2c4` = `i2c@2ac70000`（对应 `/dev/i2c-4`）
- **D-PHY 端点**：`dcphy0_in_gc05a2` = `csi2-dcphy0/ports/port@0/endpoint@2`，这是 **2-lane** 那路
- **时钟**：`<&cru 0x38>`，`clock-names = "xvclk"`，引脚 `cam_clk0m0_clk0`
- **供电**：`vcc_mipicsi0_avdd` / `vcc_mipicsi0_dovdd` / `vcc_mipicsi0_dvdd`
- **GPIO**：`reset` 在 `gpio3` 第 28 脚，`pwdn` 在 `gpio3` 第 22 脚
- **电源域**：`<&power 0x0f>`

另外确认基础 DTB 带 `__symbols__` 节点（本机有 1427 个符号），**这是 overlay 能按 label 解析的前提**。

### 4.2 关键差异：GPIO 极性

GC05A2 节点里 `reset-gpios` 和 `pwdn-gpios` 的 flag 都是 0（ACTIVE_HIGH）。**照抄会失败。**

Rockchip 各平台 BSP 里 OV5695 的惯例是：

- **`reset-gpios` 用 GPIO_ACTIVE_LOW**（flag = 1）
- `pwdn-gpios` 用 GPIO_ACTIVE_HIGH（flag = 0）

改对之后 sensor 立刻应答。**这是整件事唯一的实质卡点。**

### 4.3 overlay 全文

```dts
/dts-v1/;
/plugin/;

/ {
	compatible = "rockchip,rk3576";
};

/* 这两个是厂商预置但实际未装配的 sensor，同在 0x37；
 * 留着只会每次开机刷 probe 失败日志 */
&gc05a2_mipi0 {
	status = "disabled";
};

&imx415_mipi0 {
	status = "disabled";
};

&i2c4 {
	status = "okay";

	ov5695: ov5695@36 {
		compatible = "ovti,ov5695";
		reg = <0x36>;

		clocks = <&cru 0x38>;
		clock-names = "xvclk";
		pinctrl-names = "default";
		pinctrl-0 = <&cam_clk0m0_clk0>;

		power-domains = <&power 0x0f>;

		avdd-supply = <&vcc_mipicsi0_avdd>;
		dovdd-supply = <&vcc_mipicsi0_dovdd>;
		dvdd-supply = <&vcc_mipicsi0_dvdd>;

		/* 1 = GPIO_ACTIVE_LOW，0 = GPIO_ACTIVE_HIGH
		 * overlay 独立编译时没有 dt-bindings 头文件，只能写字面量 */
		reset-gpios = <&gpio3 28 1>;
		pwdn-gpios = <&gpio3 22 0>;

		rockchip,camera-module-index = <0>;
		rockchip,camera-module-facing = "back";
		rockchip,camera-module-name = "ov5695";
		rockchip,camera-module-lens-name = "default";

		port {
			ov5695_out: endpoint {
				remote-endpoint = <&dcphy0_in_gc05a2>;
				data-lanes = <1 2>;
			};
		};
	};
};

/* 链路必须双向一致，否则 media graph 不成形 */
&dcphy0_in_gc05a2 {
	remote-endpoint = <&ov5695_out>;
	data-lanes = <1 2>;
};
```

### 4.4 编译与安装

```sh
sudo apt-get install -y device-tree-compiler

dtc -@ -I dts -O dtb -o tspi-3m-csi0-ov5695.dtbo tspi-3m-csi0-ov5695.dts
```

编译会有若干 warning（`graph connection is not bidirectional`、`Relying on default #address-cells` 之类），都是 dtc 看不到基础设备树导致的常规 lint，可忽略。

装到 overlay 目录并在 `overlays.ini` 里登记：

```sh
sudo cp tspi-3m-csi0-ov5695.dtbo /boot/overlays/
sudo cp /boot/overlays/overlays.ini /boot/overlays/overlays.ini.bak
```

追加一段：

```ini
[group:csi-camera]
type = group
name_zh = CSI 摄像头
name_en = CSI Camera

[tspi-3m-csi0-ov5695.dtbo]
enabled = false
name_zh = CSI0 摄像头 OV5695
name_en = CSI0 Camera OV5695
group = csi-camera
```

**这块板的 overlay 由 `/usr/local/bin/ovtree` 管理**（需 sudo），它负责同步 `/boot/overlays/.ubootenv`。手改 ini 之后必须用它启用才会生效：

```sh
sudo ovtree list                                  # 确认已登记
sudo ovtree enable tspi-3m-csi0-ov5695.dtbo
sudo reboot
```

出问题回退：

```sh
sudo ovtree disable tspi-3m-csi0-ov5695.dtbo && sudo reboot
```

## 五、验证

### 5.1 驱动探测成功

```sh
dmesg | grep -i ov5695
```

```
ov5695 4-0036: driver version: 00.01.04
ov5695 4-0036: Detected OV005695 sensor
rockchip-csi2-dphy csi2-dcphy0: dphy0 matches m00_b_ov5695 4-0036: bus type 5
```

看到 `Detected OV005695 sensor` 就成了。之前是 `Unexpected sensor id(000000)`。

### 5.2 链路成形

```sh
media-ctl -d /dev/media3 -p | grep -E "^- entity|ENABLED"
```

`rkisp-isp-subdev` 的 sink 上多出了 `<- "rkcif-mipi-lvds":0 [ENABLED]`，整条链路接通。同时 `/dev/video0` 到 `/dev/video10` 出现（之前 video0 是 No such device）。

### 5.3 真的能出图

主通路是 `rkisp-vir0` 的 mainpath：

```sh
v4l2-ctl -d /dev/video33 --list-formats-ext
# UYVY / NV16 / NV61 / NV21 / NV12 / NM21 / NM12，最高 2592x1944

v4l2-ctl -d /dev/video33 --set-fmt-video=width=1920,height=1080,pixelformat=NV12 \
         --stream-mmap --stream-count=10 --stream-to=/tmp/cap.yuv
ls -l /tmp/cap.yuv
# 31104000 字节
```

**尺寸自检**：`1920 × 1080 × 1.5 = 3110400`，`× 10 帧 = 31104000`，分毫不差。

**内容自检**（避免"能出流但全黑"）：

```sh
python3 -c "
d=open('/tmp/cap.yuv','rb').read(3110400); y=d[:1920*1080]
print('min=%d max=%d avg=%.1f 灰度种类=%d' % (min(y),max(y),sum(y)/len(y),len(set(y))))"
# min=9 max=255 avg=83.3 灰度种类=247
```

灰度种类 247 说明是真实画面；全黑或全白只会有一两种值。

### 5.4 设备路径要用稳定形式

`/dev/videoNN` 的编号会漂——启用摄像头后 CIF 节点整体插入，编号整体后移。用 by-path：

```sh
ls -l /dev/v4l/by-path/ | grep rkisp-vir0
# platform-rkisp-vir0-video-index0 -> ../../video33
```

应用配置里写 `/dev/v4l/by-path/platform-rkisp-vir0-video-index0`。

## 六、经验

**第一，先定位链路断在哪一环，再动手。** EPIPE 不是"这个节点坏了"，是"上游没数据"。从报错节点顺着 media 拓扑往上游走，一直走到 dmesg 里那句 `No active sensor`，问题就定死了。中间任何一步猜测都会浪费大量时间。

**第二，参数从本机设备树扒，不要从网上抄。** 同接口已有的 sensor 节点就是最准确的模板——供电轨、时钟号、引脚号都是板子实际接法。网上文章的价值在于告诉你**哪些地方不能照抄**（本例就是极性）。

**第三，i2cdetect 扫不到不等于硬件坏。** sensor 通常要 MCLK 才响应 I2C，而 MCLK 由驱动使能。没有设备树节点 → 没有驱动 → 没有时钟 → 扫不到。判断硬件死活要看 dmesg 里驱动 probe 的日志，不是看 i2cdetect。

**第四，验证要验到内容。** 文件非 0 字节只能说明流起来了。字节数对不对（分辨率×格式系数×帧数）验的是格式协商，灰度分布验的是真的有光进来。三层都过才算通。

## 七、速查

- **模块**：OV5695，5MP，2-lane MIPI，I2C 地址 0x36
- **接口**：MIPI-CSI0 → `i2c4` / `csi2-dcphy0` 的 2-lane 端点
- **通路**：`sensor → csi2_dcphy0 → mipi0_csi2 → rkcif_mipi_lvds → rkisp_vir0 → rkvpss`
- **出图节点**：`/dev/video33`，稳定路径 `/dev/v4l/by-path/platform-rkisp-vir0-video-index0`
- **格式**：UYVY / NV12 / NV16 / NV21 / NM12，最高 2592×1944，多平面（MPLANE）
- **overlay 工具**：`sudo ovtree list | enable | disable | status`
- **硬编码器**：RK3576 **没有 V4L2 M2M 编码器**，硬编走 MPP（`/dev/mpp_service`），另有 `/dev/rga` 可做格式转换

## 八、遗留问题：画面发绿（3A/ISP 标定未打通）

出图后画面明显偏绿，且移动摄像头会拖影。两者同源：**rkaiq 3A 没有运行**，导致自动白平衡、自动曝光全部缺席，曝光/增益停在驱动默认值。

### 已经确认的事实

**发绿不在编码或传输链路上。** 直接从 `/dev/v4l/by-path/platform-rkisp-vir0-video-index0` 抓的原始 NV12（未经编码器、未经 P2P）本身就是绿的，色度 U=112 / V=115（中性为 128）。

**移动模糊是曝光时间造成的，当前光照下无解。** 传感器控制实测：

```
exposure      : min=4  max=2020  value=1104     ≈ 16.5ms
analogue_gain : min=16 max=248   value=248      ← 顶在最大值
```

30fps 的帧周期是 33ms，曝光占了一半，必然拖影。但缩短曝光会让画面掉到不可用（实测 Y 均值 53 → 23，暗部占比 51% → 78%），而 `digital_gain` 在这条管线上**完全无效**（设 3 倍亮度不变，原因见下）。也就是说光线不足时短曝光和足够亮度不可兼得，开灯或白天会自然改善。

**ISP 和所有 subdev 上不存在任何白平衡控制**，白平衡只能走 rkaiq 3A 管线，没有第二条路。

### IQ 标定文件：已构造成功

板子 `/etc/iqfiles/` 下只有 9 个传感器的 json，没有 OV5695。公开渠道能找到的 ov5695 标定只有 **isp21** 格式和更老的 xml，而本板是 **rkaiq 6.9.0 / ISP39**：

```
dpkg -l | grep rkaiq     → camera-engine-rkaiq 6.9.0 (rkisp v39, rk3576)
strings /usr/lib/librkaiq.so | grep Isp39   → CamCalibDbV2ContextIsp39_t
```

两代 schema 的算法段名和模块命名完全不同（`scene_isp39` 30 个模块 vs `scene_isp21` 27 个，且命名体系不一样），不能直接用。

**可行做法：以 ov16880 为模板改。** 板载 `ov16880_KYT-11379-V1_default.json` 是 isp39 原生格式，且同为 OmniVision，其 `Gain2Reg` 与 isp21 里 OV5695 的真实标定**逐值相同**：

```
Gain2Reg   : [1, 15.5, 16, 0, 1, 16, 248]     ← 与实测 analogue_gain min=16 max=248 吻合
CISGainSet : CISAgainRange Max 15.5, CISIspDgainRange Max 1  ← 解释了 digital_gain 为何无效
```

只需改三处：`resolution` 改 2592x1944、`CISTimeSet.Linear.CISTimeRegMin` 改 4（与实测 exposure min=4 吻合）、`CISLinTimeRegMaxFac` 用 OV5695 的值。文件名必须是 **`ov5695_ov5695_default.json`**——名字由 overlay 里的 `rockchip,camera-module-name` 和 `lens-name` 决定，不是 `ov5695_TongJu_CHT842-MD` 那种。

改完后 3A **能完整初始化并真正控制传感器**（曝光 1104→182、增益 248→16 都是 AE 写入的）：

```
rk_aiq_uapi2_sysctl_init success. iq:/etc/iqfiles//ov5695_ov5695_default.json
rk_aiq_uapi2_sysctl_prepare success. mode:0
```

### 真正的卡点：ISP 停在离线回读模式，拿不到 RAW

3A 一旦运行，采集就完全不出帧（关掉 3A 立即恢复）。日志指向：

```
AiqCamHw_start success. isGroup:0, isOnline:0, isMultiIsp:0
CAMHW:E:trigger_isp_readback buf not ready !
dmesg: rkcif-mipi-lvds: stream[0] stopping finished, dma_en 0x0
```

rkaiq 判定为**离线回读模式**，等着从内存读 RAW 喂 ISP，但 CIF 的 DMA 没开（`dma_en 0x0`），回读永远等不到缓冲。

已逐项验证并**排除**的猜测：

- 设备树连接是对的：`rkisp-vir0/port/endpoint@0 → rkcif-mipi-lvds-sditf/port/endpoint`，完整通路 `sensor → csi2 → rkcif → sditf → rkisp-vir0` 存在
- 用 media-ctl 切换直通/回读链路（两个方向都试过）→ 模式判定不变
- 屏蔽空闲的 rkisp1/rkisp2 实例 → 拓扑报错消失，仍是离线
- 从 rkvpss 节点取流 → 也不出帧
- 手动并发启动 CIF RAW 采集（video0 能出 258MB 数据）→ ISP mainpath 仍 0 帧
- 删 `FakeCamera0.json` → rkaiq 直接起不来，该文件是必需的
- `rkisp_demo` 属于旧的 rkisp1 驱动（camera-engine-rkisp 2.3.0），断言 `sensor_subdev` 失败，不兼容新驱动

构造的 IQ 文件本身没有明显缺陷：报错里的 `AWB:E:no rgbySpace config` 和 `LSC meshGrid` 属于 `FakeCamera0`（cid[-1]）那一路，我们这份（cid[0]）的对应字段与板载 gc05a2 完全一致。

### 下一步需要的外部输入（已被下一节的 overlay 方案部分解决，见九）

继续往下要么拿到 Rockchip RK3576 SDK 里 rkaiq 6.9 的在线/离线模式配置说明，要么向立创/模组厂索要已验证的 OV5695 + ISP39 配置。**注意本板官方从未提供 camera overlay**（`/boot/overlays/` 里只有两个 DSI 屏的），内核 `CONFIG_VIDEO_OV5695=y` 只是把驱动编进去了，板级集成和 ISP 调优都没做过，很可能官方也没验证过这条链路。

### 板子状态（已过时，见九）

以下是本节写作时的状态，**已被第九节的发现取代**：`rkaiq_3A.service` 当时保持 `disable`，摄像头能正常出图但画面发绿。现在的结论是：仅靠 IQ 文件不足以让 3A 在默认拓扑下出帧（见九），发绿问题仍未彻底解决。

**另注**：重启后**首次**抓帧经常失败，第二次起正常，属于该平台的冷启动现象，不是故障。

## 九、overlay 修复 isOnline，但引入新的 MIPI CRC 死锁

> **本节与第十节的结论已被第十一节修正。** 当时把 CRC 死锁归因于硬件信号裕量和内核 PHY 驱动缺陷，实际上它是本节引入的 `tspi-3m-isp-single.dtbo` 造成的；移除该 overlay 后 CRC 风暴不再出现。下面的排查过程仍有参考价值，但**不要照搬结论**。

### 根因：默认多实例（离线回读）拓扑下 3A 拿不到帧，是拓扑问题不是标定问题

第八节遗留的 `isOnline:0` / `trigger_isp_readback buf not ready` 问题，根因是：`rkisp-vir0/1/2` 是同一块 ISP 硬件的三个虚拟实例（time-multiplexed），设备树默认三个都 `status = "okay"`。只要不止一个 vir 处于启用状态，驱动就判定为多摄像头场景，强制走离线回读模式——而回读模式在这块板子上从来没有真正工作过（`dma_en 0x0`，永远等不到缓冲）。这与 IQ 标定文件是否正确无关：即使标定文件完全正确，3A 在这个拓扑下依然拿不到帧。

**修复**：新增设备树 overlay `tspi-3m-isp-single.dtbo`，禁用 `rkisp_vir1` / `rkisp_vir2`，只留 `rkisp-vir0`。板端操作：

```sh
dtc -I dts -O dtb -o /boot/overlays/tspi-3m-isp-single.dtbo /tmp/tspi-3m-isp-single.dts
# overlays.ini 只是 ovtree status/list 用的元数据，U-Boot 实际读的是 .ubootenv，
# 必须先 disable 再 enable 才会触发 .ubootenv 真正重写：
ovtree disable tspi-3m-isp-single.dtbo
ovtree enable  tspi-3m-isp-single.dtbo
reboot
```

（overlay 源码见 `/tmp/tspi-3m-isp-single.dts`，本仓库暂未收录，后续应迁到 `boards/LINUX/TaishanPi_3/` 下随板级配置一起维护。）

生效后 `rkisp-vir1/vir2` 变为 `disabled`，媒体设备数从 9 降到 7，ov5695 的 subdev 编号从 `/dev/v4l-subdev5` 漂到 `/dev/v4l-subdev3`（少了两个 ISP 实例，编号整体前移，排查时要重新用 `media-ctl -p` 定位，不能死记编号）。3A 首次在这个拓扑下真正跑起来：`isOnline:1`，AE 主动调整曝光（1104→182→2429）和增益（248→16→49），色度 V 通道从 115 提升到 126，实拍验证肤色和物体颜色明显改善。

### 新问题：online 模式下 3A 一启动就导致 MIPI D-PHY CRC 死锁

三种状态反复验证，**确定性可复现**（不是偶发）：

| overlay（拓扑） | 3A 运行 | 结果 |
|---|---|---|
| 不加（默认多实例/离线） | 否 | 稳定出图，0 CRC，但发绿 |
| 不加（默认多实例/离线） | 是 | `isOnline:0`，readback 一直不 ready，**0 帧**（本节开头的老问题） |
| 加（单实例/在线） | 否 | 稳定出图，0 CRC，仍发绿（3A 没跑，色彩没矫正） |
| 加（单实例/在线） | 是 | 流启动后 **71ms 内爆发 4087 条** `MIPI_CSI2 ERR1:0x1000000 (crc,vc: 0)`，链路死锁，**0 帧**，之后再无新错误也无新帧（不是恢复，是彻底停摆），重复三次分别是 4024/4088/4088 条，量级高度一致 |

关键实测数据：

- CRC 错误全部集中在一个 71ms 的窗口内爆发（`dmesg` 时间戳 292.188253 → 292.259293），之后 30+ 秒完全静默、零帧——说明这是流启动瞬间 D-PHY 同步失败并锁死，不是持续抖动，也不会自愈。
- 排除是 3A 主动进程存在导致：`systemctl mask` 彻底停掉 3A 进程后，仅仅"拓扑处于单实例"本身不会触发 CRC（上表第三行验证）；只有 3A 真正运行、驱动其自身 device manager 管线时才触发。
- 排除是 sensor 模式切换导致：3A 运行时查询 `/dev/v4l-subdev5` 的 `VIDIOC_SUBDEV_G_FMT`，格式仍是 2592x1944 raw bayer，与不跑 3A 时一致。
- vblank 余量：默认 `vertical_blanking=80`、`horizontal_blanking=368`、`pixel_rate=180MHz`，算出的场消隐时间 ≈1315us，理论上高于 Rockchip 文档里"online 模式要求 vblank ≥ 1000us"的门槛，不像是卡在临界点——但没能实测验证调大 vblank 是否能压住 CRC，因为 `v4l2-ctl -c vertical_blanking=xxx` 在这个 subdev 上始终报 `unknown control`（`--list-ctrls` 能看到该控件，但 `-c` 设置不进去，怀疑与 sensor 驱动的电源状态/控件可见性收窄有关，未查清）。
- 反编译官方摄像头 overlay `tspi-3m-csi0-ov5695.dtbo` 发现该板基础设备树是"三选一摄像头模组"设计（`gc05a2`/`imx415`/`ov5695` 三选一接在 CSI0），vir1/vir2 大概率对应另外两个物理 MIPI 口，禁用逻辑本身没问题，但没能找到额外的 D-PHY 时序类属性能解释 CRC。

### 现状与结论

色彩矫正（3A）与稳定抓帧在这块板子上**当前互斥**：默认拓扑下 3A 喂不出帧，切单实例拓扑后 3A 又会把物理链路锁死。两条路径都不是 SDK 层面能调的参数问题，已经触到 Rockchip 内核 `rkcif`/`rkisp` 驱动或本板设备树更底层的东西（D-PHY 时序、online 模式实时性约束），没有内核源码或厂商完整 DTS 难以精确定位。

**用户决策（2026-08-14）**：继续排查 online 模式 CRC 根因，而不是回退到发绿状态。下一步方向：联系立创/模组厂要 D-PHY 时序相关的完整参考 DTS，或在 Rockchip 内核仓库（`rockchip-linux/kernel`）搜索/提交类似 `MIPI_CSI2 ERR1` + `rkaiq online` 组合的 issue。

## 十、CRC 死锁根因定位（有内核源码依据）

> **结论已被第十一节修正**，原因同上。本节的证伪清单（CMA、寄存器写时序、应用层重试等逐项排除）依然成立且有用。

### 排除清单（逐项用真实实验证伪，非猜测）

| 假设 | 验证方法 | 结果 |
|---|---|---|
| CMA 内存碎片化导致 DMA 缓冲区分配失败 | 通过 overlay 追加 `cma=768M`（改 `/chosen/bootargs`），从默认 16MB 扩到立创三摄文档验证过的 768MB | **证伪**：扩容后两次开机仍是完全一致的 4088 条 CRC、0 帧，和内存大小无关 |
| 3A 主动写曝光/增益寄存器与流启动时序竞争 | 用 ftrace `events/i2c/i2c_write` 精确抓取 I2C 总线时间戳，与 dmesg CRC 爆发时间戳（monotonic 时钟，可直接对齐）交叉核对 | **证伪**：CRC 爆发前 4 秒起，包括无关的 sugov/kworker 后台 I2C 流量在内，总线上完全没有任何写操作 |
| 应用层重试（STREAMOFF/STREAMON）能否清掉坏状态 | 同一失败状态下连续重试 3 次 | **证伪**：CRC 计数器（4088）三次重试后纹丝不动，0 帧 |
| 重启 `rkaiq_3A_server` 用户态进程能否清掉坏状态 | `systemctl restart rkaiq_3A` 后重测 | **证伪**：仍是 4088/0 帧，说明坏状态在内核态而非 3A 进程内存里 |
| 手动 `unbind`/`bind` PHY 驱动能否软复位 | `echo csi2-dcphy0 > .../rockchip-csi2-dphy/unbind` 后 `bind` | unbind 成功但 bind 报 `Invalid argument`，无法干净重新 probe |
| 电源域挂起/恢复能否复位 PHY | 读 `/sys/kernel/debug/pm_genpd/pm_genpd_summary` | `csi2-dcphy0` 根本不在 `vi` 电源域（只有 rkcif/isp 在其中），电源域这条路物理上够不到这个 PHY |

### 真正的错误信号

之前一直只 grep `MIPI_CSI2` 数量，没有细看完整报文。完整报文其实是：

```
(0x27c80000)MIPI_CSI2 ERR1:0x1000001 (sot sync,lane: 0) (crc,vc: 0)
```

除了 CRC，还有 **`sot sync`（帧头同步失败）错误，且明确指向 `lane: 0`**——这是 D-PHY 物理层锁定失败的典型症状，不是简单的比特翻转噪声。

### 内核驱动源码印证（friendlyarm/kernel-rockchip，nanopi6-v6.1.y 分支，同为 RK3576 + Samsung DCPHY IP）

咱们板子用的正是 Samsung 的 DCPHY combo IP（`csi2-dcphy0`，对应驱动 `phy-rockchip-samsung-dcphy.c`）。读取该文件里 `samsung_dcphy_rx_stream_on()` 的实际逻辑，关键发现：

1. **hs-settle 时序是查表算出来的，不支持设备树覆盖**。表项在 830/850/870 Mbps 附近是离散的（`{830,0x129},{850,0x12a},{870,0x12b}`），咱们 sensor 实测 `data_rate_mbps 840`，查表规则是"取第一个 `range_h >= data_rate_mbps` 的项"，所以 840 被套用了 **850 挡的时序参数**——存在小幅失配的空间。
2. **stream 引用计数用 `atomic_inc`/`atomic_dec_return`，但只有计数从 0→1 的那一次才真正做物理层配置（复位、bias、lane enable、轮询 `PHY_READY`）**，后续调用只是原子递增，不会重新校验锁定状态；而失败路径（`regmap_read_poll_timeout` 超时）和正常关闭路径对计数器的处理不对称，一旦某次 0→1 的物理配置失败，计数器很可能没有被正确清零。
3. **锁定失败没有任何重试逻辑**：`phy rx data lane N is not locked` 打印后直接 `return -EINVAL`，不会自动重试。

这三点合起来，完整解释了前面五项证伪实验的结果：一旦某次物理层锁定失败，计数器状态卡住，后续任何"重试"（无论是应用层重开流、重启 3A 进程、还是普通的软件复位）都不会再触发 0→1 这条真正做硬件配置的路径，只有整机重启（驱动重新 `probe`，计数器归零）才能给 lane 0 一次全新的、独立的锁定机会。

### 现状结论

- 这是 **OV5695 在这块板子上以 840Mbps/lane 输出、叠加 lane 0 信号裕量本身可能偏紧**，两者共同作用在"online 模式下 3A 反应式做物理层初始化"这个唯一入口上的小概率锁定失败，命中之后除整机重启外没有更轻量的恢复手段（已验证：CMA、寄存器写时序、应用层重试、3A 进程重启、PHY unbind/rebind、电源域挂起全部无效）。
- 真实 APP + P2P 完整链路验证：多次开机中约 5/6 是坏的（`sot sync` 锁定失败），仅 1/6 正常；正常时 3A 色彩矫正确认有效（AE 收敛、色度改善，见五）。
- 这是内核 PHY 驱动本身缺少重试机制导致的问题，不是我们 SDK 层能修的参数问题。真正的修复需要拿到本板对应内核源码，给 `samsung_dcphy_rx_stream_on()` 补一个"锁定失败后重试 N 次"的逻辑，并修掉引用计数在错误路径上的不对称清零。这需要厂商（立创）提供内核源码和重新编译固件的能力，属于超出 SDK 应用层范畴的工作。

## 十一、结论修正：CRC 死锁是自己引入的，发绿归属 BSP

第九、十节把 CRC 死锁归因于硬件信号裕量和内核 DCPHY 驱动缺陷，**这个结论是错的**。本节是最终结论。

### 11.1 CRC 死锁的真正来源：我们自己加的 overlay

时间线对得上：加 `tspi-3m-isp-single.dtbo`（为了让 rkaiq 出帧而把 ISP 切成单实例 online 拓扑）**之前**，采集一直稳定；加了**之后**才开始出现 `MIPI_CSI2 ERR1:0x1000001 (sot sync,lane: 0) (crc,vc: 0)` 风暴。

移除该 overlay 后实测 11 次抓帧：**一次 CRC 风暴都没有**（10 次成功，1 次纯超时且 `CRC=0`，属于第五节记过的冷启动首帧现象）。

对照第九节表格里"加 overlay + 3A"那一行的 4088 条 CRC，差异是决定性的。

**教训**：为了让某个组件（rkaiq）跑起来而改动共享的硬件拓扑，代价可能落在完全不相干的地方（MIPI 物理层稳定性），而且因为中间隔了好几层，很难反推回来。第十节那一整套内核源码分析虽然细致，但方向从一开始就错了——真正该先做的是**把自己引入的变量摘掉再测**。

### 11.2 发绿：原因确认，但不由应用层解决

**原因**：ISP 从来没有被写入白平衡增益。raw bayer 的绿色像素数量是红蓝的两倍，不做 WB 校正必然发绿。正常情况下这是 rkaiq 的职责，而 rkaiq 在本板跑不起来的根因见第八节——**出厂镜像没有 OV5695 的 IQ 标定文件**（`/etc/iqfiles/` 下 9 个传感器的 json，没有它）。

**验证过可行、但已从 SDK 中移除的方案**：ISP 参数节点 `rkisp-input-params` 只是一个普通的 v4l2 meta-output，任何进程都能写，rkaiq 只是其中一个写入者。据此实现过一套用户态 3A 并实测通过：

- **AWB**：对输出帧色度闭环，收敛到 U/V = 128.0±0.2（原始 114.3/123.2），实拍确认红/白/蓝/绿/黄全部还原
- **AE**：对亮度闭环，控制 sensor 曝光与增益，曝光上限 10ms 时亮度 Y≈67
- 全程不依赖 rkaiq、不改设备树、`CRC=0`

**移除原因**（不是因为不work，而是因为不该由我们做）：

1. **分层**：TuyaOpen 是应用 SDK，消费的是已处理好的帧。图像质量是 BSP 交付物。在应用 SDK 里直接写 ISP 寄存器等于越过整个 BSP 层。
2. **可移植性**：实现写死了 ISP39 的结构体布局和 Rockchip 节点名，还需要随源码带 236K 内核 UAPI 头。换 ISP 代次要重新对结构体，换厂商直接不适用。
3. **算法本身是玩具，而且会主动出错**：灰世界假设"画面平均色应为中性灰"。对着红墙会把红墙压成灰、大片绿植/暖光同理。真正的 AWB 需要光源估计加传感器标定模型——**这正是 IQ 文件里那 30 个算法模块的内容**。恒定发绿一眼能看出是没标定；灰世界则"时对时错"，更难排查。

### 11.3 过程中被实测证伪的路径（避免重走）

| 尝试 | 结果 |
|---|---|
| 用 ISP 自带 RAWAWB 统计做灰世界 | 统计点在 CCM **之前**，算出 b 增益 1.79，而输出中性只需 1.32，过校正偏蓝。改为对输出色度闭环则自动抵消后级全部处理，无需任何补偿常数 |
| 每帧刷新 ISP 参数 | 数秒后色度平面被抹成恒定 128，画面变纯黑白。改为仅在增益变化时下发即正常 |
| 每帧积分调增益 | 参数生效有多帧延迟，积分饱和震荡。改为"沉降→测量→步进"后一次过冲即收敛 |
| CMA 16MB→768MB | 抓帧失败与内存无关，两次开机结果完全一致（4088 条 CRC）。**已回退** |
| 1296x972 binning 换取短曝光 | 实测仅 1.4 倍灵敏度（跳采而非真 2x2 电荷合并），不足以解决拖影 |

另外记录一个模式选择的坑：OV5695 的小尺寸模式分两类——**1296x972（4:3，与全分辨率同比例）是跳采，保留完整视野**；**1280x720 / 1920x1080（16:9）是裁切窗口，视野变窄**。按"最小模式"选会选中裁切模式，等于拿视野换曝光。

### 11.4 拖影：物理限制

曝光 20.5ms 是拖影来源，而增益已顶死在最大 15.5 倍——**没有"用增益换曝光"的余量**。要把曝光压到 4ms 需要 4~5 倍的光。这是光学限制，软件无解，只能在"亮度 vs 拖影"之间取舍。

### 11.5 需要向厂商（立创/模组厂）提报的内容

1. **出厂镜像缺 OV5695 的 ISP39 IQ 标定文件**，导致 rkaiq 无法工作、画面发绿。这需要标准光源箱加色卡跑标定流程，不是写代码能替代的。文件名由 overlay 里的 `rockchip,camera-module-name` 与 `lens-name` 决定，本配置下应为 `ov5695_ov5695_default.json`。
2. **出厂镜像不提供任何 CSI 摄像头 overlay**（`/boot/overlays/` 只有两个 DSI 屏的），内核 `CONFIG_VIDEO_OV5695=y` 只是把驱动编了进去，板级集成未做。
3. 参考：Rockchip 官方认证摄像头列表中，**RK3576 一档并不包含 OV5695**（OV5695 认证的是 RK3588/RK3568）；RK3576 认证的是 IMX464、OV16885、OV16880、S5K4H5、GC05A2、IMX415、SC4336。若项目允许换模组，选认证过的型号可直接绕开本文档全部问题。

### 11.6 当前板子状态

```
/boot/overlays/.ubootenv:  overlays=tspi-3m-csi0-ov5695.dtbo   # 只剩摄像头这一个必需项
CmaTotal:                  16384 kB                            # 已回退到默认
rkaiq_3A.service:          disabled
```

出图正常（1280x720 NV12，30fps，CRC=0），**画面发绿**——这是这块板子加上出厂镜像的真实状态，属于已知 BSP 限制。

SDK 侧保留的只有一条与本问题相关的改动：采集线程在 dequeue 持续失败时会打印 `pipeline is armed but idle`。在此之前，摄像头一帧不出在日志里毫无痕迹，与"正常但空闲"完全无法区分。
