# 写给音视频的环形缓冲：普通队列在这儿全是坑

摄像头出帧，网络发帧，中间垫一个缓冲区。听上去就是个生产者-消费者队列，写起来十分钟。

但音视频这条链路上，**帧和帧是不平等的**（丢了 I 帧后面全废）、**迟到的数据没有价值**（三秒前的画面不如现在的）、**生产者不能等消费者**（摄像头不会因为网络卡了就停）。这三条让普通队列的每一个默认行为都变成了坑。

下面五个决策点，每个都是"看起来对的写法 → 现场表现 → 实际该怎么写"。案例代码是 TuyaOpen 的 `svc_ring_buffer`，但结论对任何音视频缓冲都适用。

## 决策一：满了之后，丢老的还是丢新的

普通队列满了，`push` 阻塞或者返回失败，让生产者等。

音视频里这么做，等的是摄像头取流线程。它一停，V4L2 的 buffer 队列很快耗尽，驱动开始丢帧，而且丢在你看不见的地方。更糟的是网络恢复之后，缓冲区里全是几秒前的画面，观众要等着把这些陈旧内容播完才能看到现在。

所以环形缓冲的答案是：**写者永不阻塞，直接覆盖最老的槽位。**

```c
tal_mutex_lock(st->lock);
node = &st->nodes[st->write_idx % st->slot_cnt];
memcpy(node->raw_data, addr, size);
/* ... */
st->write_idx = (st->write_idx + 1) % st->slot_cnt;
tal_mutex_unlock(st->lock);
```

没有满不满的判断，写就完了。代价是读者可能被"套圈"，这个代价怎么处理是决策三的事。

顺带一提，槽位是预分配好的，每个槽持有一块固定大小的内存：

```c
for (i = 0; i < st->slot_cnt; i++) {
    st->nodes[i].raw_data = (uint8_t *)RBUF_MALLOC(st->max_frame_size);
    /* ... 失败要回滚已分配的 ... */
}
```

运行期不做分配。取流线程是硬实时路径，一次 malloc 抖动就是一帧的抖动，而且长时间跑下来堆会碎。

## 决策二：槽位数量是内存预算，不是缓冲时长

参数长这样：`fps`、`max_buffer_seconds`。很自然地会写 `slot_cnt = fps * seconds`。

然后在 MCU 上炸了。25fps × 2 秒 = 50 个槽，每槽按码率算出来几十上百 KB，几 MB 内存 —— PSRAM 上没有这个空间。

真实的写法要认清一件事：**这个参数表面上是时长，实际上是内存预算。**

```c
/*
 * Slot count is really a memory budget: each slot holds one encoded frame.
 * 8 slots is 0.32s at 25fps, thin enough that a brief reader stall forces the
 * skip path below. MCUs pay for this out of scarce PSRAM and keep the small
 * cap; Linux has no such constraint, so let the requested fps*seconds stand.
 */
#if defined(SYSTEM_LINUX) && (OPERATING_SYSTEM == SYSTEM_LINUX)
#define RBUF_MAX_SLOTS 64
#else
#define RBUF_MAX_SLOTS 8
#endif
```

MCU 上 8 个槽，25fps 下只有 0.32 秒的余量。这个数字小到读者稍微慢一下就会被套圈——所以决策三的跳帧路径不是异常分支，**在 MCU 上它是常态路径**，必须按常态来设计。

单帧大小也一样要有天花板，从码率推、但两头都夹住：

```c
st->max_frame_size = (st->bitrate_kb * 1024 * 3) / 16;  /* 约 1.5 倍平均帧 */
if (st->max_frame_size < (64 * 1024))  st->max_frame_size = 64 * 1024;
if (st->max_frame_size > MAX_MEDIA_FRAME_SIZE) st->max_frame_size = MAX_MEDIA_FRAME_SIZE;
```

I 帧比 P 帧大好几倍，纯按平均码率算会经常放不下；不设上限又会被一个异常的大帧撑爆。

## 决策三：读者跟不上时，跳到哪一帧

这是全篇最重要的一条。

读者落后太多的时候必须跳帧，没得商量。问题是**跳到哪儿**。

直觉答案是"跳到最新的一帧"，追上直播嘛。这个答案是错的，而且错得很隐蔽。

因为最新的那一帧大概率是 P 帧。P 帧只有和前一帧的差分，对端拿到它无法解码，只能扔掉，然后继续扔掉后面所有 P 帧，**一直等到下一个 I 帧才能重新起解**。GOP 如果是 2 秒，观众就是黑屏或者定格 2 秒。

现场表现：一卡就卡好几秒，而且"越卡越卡"——因为每次跳帧都触发一次新的等待期。看日志一切正常，帧在发，没有报错。

正确的跳法是跳到**环里还留着的最新 I 帧**：

```c
if (best != NULL && newest_seq > 0 && (newest_seq - best->seq_no) > (st->slot_cnt / 2)) {
    RING_BUFFER_NODE_T *newest_key = NULL;

    /*
     * Too far behind to catch up in sequence. Skipping is unavoidable here,
     * but landing on a P-frame hands the peer a stream it cannot decode
     * until the next I-frame, which is seen as a multi-second freeze. Jump
     * to the newest I-frame still held instead; if the ring has none, stay
     * in sequence and let the reader crawl forward rather than emit a jump
     * nothing can decode.
     */
    for (i = 0; i < st->slot_cnt; i++) {
        RING_BUFFER_NODE_T *n = &st->nodes[i];
        if (n->seq_no == 0 || n->size == 0 || n->seq_no <= user->read_seq) continue;
        if (n->type != E_VIDEO_I_FRAME) continue;
        if (newest_key == NULL || n->seq_no > newest_key->seq_no) newest_key = n;
    }
    if (newest_key != NULL) {
        *skip_from = best->seq_no;
        *skip_to   = newest_key->seq_no;
        best = newest_key;
    }
}
```

三个细节：

**触发阈值是 `slot_cnt / 2`，不是"满了才跳"。** 等到写指针追上读指针，数据已经被覆盖了，那时候跳是补救；提前半圈跳是预防。

**环里一个 I 帧都没有的时候，不跳。** 宁可让读者按顺序慢慢爬，也不要发一个对端解不了的跳跃。这是"没有好选择时选损害最小的"——爬行只是延迟高，跳到 P 帧是画面直接坏掉。

**跳帧要记账。** 丢帧是实打实的质量事件，不该被悄悄咽下去：

```c
static void __rbuf_report_skip(RBUF_STREAM_T *st, uint32_t skip_from, uint32_t skip_to)
{
    if (skip_to == 0) return;
    if ((st->skip_cnt++ % 30) == 0) {
        PR_WARN("ring reader behind, skip seq %u -> %u (I-frame), count %u",
                skip_from, skip_to, st->skip_cnt);
    }
}
```

计数器放在 `st`（每路流一份）而不是函数里的 `static`。主码流和子码流同时在跑的时候，static 计数器被两路共用，`% 30` 的降频按混合值触发，日志就再也说不清是哪一路在丢帧了。这个错误在统计代码里极其常见，值得单拎出来记住：**限流用的计数器，作用域必须和被统计的对象一致。**

还有一点：`__rbuf_report_skip` 在锁外调用。日志函数可能很慢（串口打印尤其慢），不能压着互斥锁做。

## 决策四：给读者指针，还是给读者拷贝

这是个正确性问题，不是性能问题。

省内存的写法是返回环内槽位的指针，读者直接用，零拷贝：

```c
RING_BUFFER_NODE_T *tuya_ipc_ring_buffer_get_frame(handle, is_retry);
```

问题在于，函数返回的那一刻锁就放开了，**写者随时可能覆盖这个槽**。而且注意时机：读者慢的时候最容易被覆盖，而读者慢正是它需要这个数据的时候。表现是花屏、半帧、解码器报错，偶发、难复现，压测才出。

所以更安全的接口是在锁内拷出来：

```c
tal_mutex_lock(st->lock);
best = __rbuf_pick_locked(user, st, &skip_from, &skip_to);
if (best != NULL) {
    if (best->size > dst_cap) {
        PR_ERR("ring frame %u exceeds reader buffer %u", best->size, dst_cap);
        rt = OPRT_INVALID_PARM;
    } else {
        /* Copied here rather than by the caller: the slot is the writer's
         * to reuse the instant this lock is dropped. */
        memcpy(dst, best->raw_data, best->size);
        *out = *best;
        out->raw_data = dst;
        user->read_seq = best->seq_no;
        rt = OPRT_OK;
    }
}
tal_mutex_unlock(st->lock);
```

关键是**拷贝必须发生在锁内**。"拿指针出来再拷"和"锁内拷"看着差不多，实际上前者完全没有保护——竞态窗口就在那两行之间。

零拷贝接口保留了，但头文件里把风险说死：

```c
 * @warning The payload is only borrowed, and the writer may overwrite this very
 *          slot the moment this call returns. Prefer
 *          tuya_ipc_ring_buffer_read_frame(), which copies under the lock;
 *          reach for this only where the caller can guarantee it consumes the
 *          data before the ring can wrap.
```

这是对待危险接口的合理姿态：**不删掉，但让默认选择是安全的那个，并且把"什么条件下才能用危险的那个"写在签名旁边。**

## 决策五：读者重连时，游标归零还是前进

读者断开重连，或者新来一个观众，游标该置到哪儿？

`read_seq = 0` 是最自然的写法，意思是"从头开始读"。

结果是：观众点开直播，先看到环里存的所有旧画面（8 槽是 0.3 秒还好，64 槽就是两秒多的历史），快速播完才追上现在。观众的感受是"点开先卡了一下"或者"画面时间不对"。

直播的语义是**从现在开始**，所以游标要前进到最新：

```c
/*
 * Forward to the newest frame held, which is what a reader attaching or
 * reattaching wants. Rewinding to zero instead - as this used to - makes
 * the next read start from the oldest slot, so a viewer that reconnects is
 * served the whole ring of stale video before catching up to live.
 */
tal_mutex_lock(st->lock);
user->read_seq = 0;
for (i = 0; i < st->slot_cnt; i++) {
    if (st->nodes[i].seq_no > user->read_seq) {
        user->read_seq = st->nodes[i].seq_no;
    }
}
tal_mutex_unlock(st->lock);
```

注释里 "as this used to" 那句是实情——这个函数原来就是置零的。这类 bug 的特征是**没有任何报错，功能"是好的"，只是体验差**，所以能活很久。

顺带说一句这里为什么要遍历所有槽位找最大 seq，而不是直接读 `write_idx` 前一个：因为环可能还没写满，也可能刚被 reset，遍历是唯一不依赖填充状态假设的写法。8 到 64 个槽，遍历的成本可以忽略。

## 一个反复出现的模式

回头看，五个决策点里有三个是同一件事的不同版本：

- 跳到最新帧（错） vs 跳到最新 I 帧（对）
- 借指针（危险） vs 锁内拷贝（安全）
- 游标归零（自然） vs 游标前进（正确）

三处的错误写法都**不会报错、不会崩溃、测试也能过**。它们的代价全部落在画面质量和观感上，而这些指标在单元测试里是不可见的。

音视频这条链路的调试难点就在这儿：**大部分故障不表现为错误，而表现为"能用，但不好"。** 所以写这类代码的时候，需要主动把每个决策点的取舍写进注释——因为后面接手的人（包括三个月后的你）看到的是一段"正常工作"的代码，没有任何线索提示这里曾经有过选择。
