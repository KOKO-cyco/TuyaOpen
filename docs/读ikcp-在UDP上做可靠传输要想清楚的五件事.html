读 ikcp.c：在 UDP 上做可靠传输，要想清楚的五件事

KCP 用一千多行 C 代码实现了一套可靠传输。这篇不是逐行翻译， 而是挑出五个每个自研传输层都必须做的决策，看 KCP 是怎么选的、代价是什么， 以及要在它上面做扩展时该怎么下手。

代码 ikcp.c，约 1500 行 依赖 无（只要一个发包回调） 适合 做实时流、隧道、P2P 的人

先回答"为什么不用 TCP"。TCP 的设计目标是在共享网络里公平且高效地搬运字节， 为此它愿意等——等重排、等拥塞窗口长大、等超时退避。 实时音视频的目标不一样：晚到的数据没有价值。 一帧画面迟到 3 秒，重传成功了也只是浪费带宽。 KCP 的所有取舍都可以从这句话推出来：它用更多的带宽换更低的延迟。

重传的三个触发条件

可靠传输的核心就一件事：怎么知道该重发了。 KCP 的答案全在 ikcp_flush() 的这段判断里： 

if (segment->xmit == 0) {
    needsend = 1;                       // (1) 从没发过
} else if (_itimediff(current, segment->resendts) >= 0) {
    needsend = 1;  is_timeout = 1;      // (2) 超时了
} else if (segment->fastack >= resent) {
    if ((int)segment->xmit <= kcp->fastlimit || kcp->fastlimit <= 0) {
        needsend = 1;  is_fastack = 1;  // (3) 被跳过太多次
    }
}

首发

xmit == 0

还没发过的新数据。注意首发也走这个统一循环，不是单独一条路径——少一套代码就少一处不一致。

超时重传

current ≥ resendts

兜底手段，什么都没收到时唯一的依靠。代价是要等一个 RTO，是三者里最慢的。

快速重传

fastack ≥ resent

后面的包被确认了，说明这个包大概率丢了。不用等超时，立刻补发。延迟敏感场景的主力。

fastack 是怎么涨的？收到 ACK 时，KCP 会记下这批 ACK 里最大的序号， 然后给发送缓冲里所有比它小、且还没被确认的包各记一笔"你被跳过了"。 跳过次数达到 fastresend（典型配置是 2）就触发重传。

这里有个容易被忽略的保护：segment->xmit <= kcp->fastlimit。 已经重发过很多次的包，不再享受快速重传。 因为反复触发快重传通常意味着链路真的坏了，这时候继续激进补发只会加剧拥塞。 默认 IKCP_FASTACK_LIMIT = 5。

RTO 怎么算，以及 KCP 在哪儿偷了懒

超时重传要有个"超时时间"。这个值算大了反应慢，算小了误判丢包、白白重发。KCP 用的是经典公式：

kcp->rx_rttval = (3 * kcp->rx_rttval + delta) / 4;   // 抖动的滑动平均
kcp->rx_srtt   = (7 * kcp->rx_srtt + rtt) / 8;      // RTT 的滑动平均

rto = kcp->rx_srtt + _imax_(kcp->interval, 4 * kcp->rx_rttval);
kcp->rx_rto = _ibound_(kcp->rx_minrto, rto, IKCP_RTO_MAX);

RTO = 平均 RTT + 4 倍抖动，这和 TCP 是一致的。 值得注意的是两个夹逼：下界 rx_minrto，上界 60 秒。

下界这个值，是 KCP "低延迟优先"最直接的体现：

模式最小 RTO超时后的退避适用
普通 nodelay=0 100 ms rto += max(rto, rx_rto)，约等于翻倍 带宽敏感、能忍延迟
极速 nodelay=1 30 ms rto += rto / 2，只涨 1.5 倍 实时流、互动

TCP 超时后是指数退避（每次翻倍），KCP 在极速模式下只涨 1.5 倍。 这意味着持续丢包时 KCP 会比 TCP 重发得频繁得多。 这不是 bug，是明码标价的取舍：用带宽换延迟。

选型时要认清的代价

这个取舍在专网、隧道、一对一 P2P 里是划算的。但如果你的流量要和别人共享一条拥挤的链路， KCP 的激进重传会挤占其他连接，也会让自己在丢包率高时陷入"越丢越发、越发越丢"。 把 KCP 当成"更快的 TCP"来用，是最常见的误用。

拥塞控制：原版够用吗

KCP 自带的拥塞控制是教科书式的 Reno：

if (kcp->cwnd < kcp->ssthresh) {
    kcp->cwnd++;                    // 慢启动：每个 RTT 翻倍
    kcp->incr += mss;
} else {
    // 拥塞避免：每个 RTT 才涨大约一个包
    if (kcp->incr < mss) kcp->incr = mss;
    kcp->incr += (mss * mss) / kcp->incr + (mss / 16);
    ...
}

问题出在拥塞避免阶段：每个 RTT 只涨一个包。 假设 RTT 是 50ms，窗口要从 10 个包长到 100 个包，需要 90 个 RTT，也就是 4.5 秒。

对文件传输，4.5 秒无所谓。对直播开流，这 4.5 秒正好是观众点开画面的头几秒—— 这段时间里编码器在按目标码率产出，而发送窗口还没长到能承载它， 数据堆在队列里，最后被丢掉。用户的感受是"刚点开总要卡一下"。

所以生产环境里换成了 CUBIC，它的窗口增长是三次函数，几个 RTT 就能逼近上一次的拥塞点：

if (kcp->cong != NULL) {
    /*
     * CUBIC. Stock growth below raises cwnd by roughly one packet per
     * RTT once past slow start, so reaching the capacity of a fast
     * link takes many round trips - long enough that the opening
     * seconds of a live stream queue up and get dropped. CUBIC gets
     * there in a few RTTs instead.
     */
    ikcp_cong_cubic_on_ack(kcp, (IUINT32)_itimediff(kcp->snd_una, prev_una));
} else if (kcp->cwnd < kcp->rmt_wnd) {
    ... 原版逻辑保持不动 ...
}

顺带一提，KCP 还提供了 nocwnd=1 直接关掉拥塞控制。 这在完全可控的专线上能榨出性能，但在公网上等于把网络当成自己家的—— 它是一个需要你对链路负全责的开关，不是一个性能选项。

给别人的库做扩展，三条纪律

把 CUBIC 挂进 KCP 这件事本身，比 CUBIC 的公式更值得学： 怎么在一个上游会持续更新的三方库里插入自己的逻辑。

纪律一：留钩子，不改逻辑

结构体里加一个不透明指针，原有字段一个不动：

struct IKCPCB {
    ...
    /* CUBIC congestion control state; NULL falls back to stock KCP growth */
    void *cong;
};

纪律二：扩展失败要能降级，不能失败

/*
 * CUBIC is what the shipping TuyaOS mid_p2p registers here. If it cannot
 * allocate, kcp->cong stays NULL and every call site below falls back to
 * the stock KCP growth rather than failing the connection.
 */
(void)ikcp_cong_cubic_init(kcp);

注意这里连返回值都不检查——因为失败是被允许的。 分配不出内存时 cong 保持 NULL，所有调用点自动走原版路径，连接照常建立。 优化模块挂不上就退回基础实现，而不是让整个连接失败，这个原则在资源紧张的嵌入式上尤其重要。

纪律三：跟着宿主的资源管理走

KCP 允许调用方替换内存分配器（ikcp_allocator()）， 比如在 MCU 上把它指到 PSRAM。原来 ikcp_malloc 是 static 的， 扩展模块用不了，于是把它导出： 

/* Not static: the congestion control module allocates its per-connection state
 * and must go through the same hook, or that state lands in a different memory
 * pool than the rest of the transport. */
void *ikcp_malloc(size_t size);
void  ikcp_free(void *ptr);

如果扩展模块直接用 malloc，它的状态会落在 C 库堆上， 而传输层本体在 PSRAM 里。平时看不出问题，直到某天内存统计对不上、 或者某个平台的 C 库堆小到装不下几十个连接的拥塞状态。 扩展模块必须和宿主用同一套资源管理，这条在内存、线程、日志上都成立。

一个真实的 bug：窗口被减了两次

接上面的改造，有个坑藏得很深，值得单独讲。

原版 KCP 在 flush 的末尾这样处理拥塞窗口：

if (change) {           // 发生过快速重传
    kcp->ssthresh = inflight / 2;
    kcp->cwnd = kcp->ssthresh + resent;
}

if (lost) {             // 发生过超时重传
    kcp->ssthresh = cwnd / 2;
    kcp->cwnd = 1;      // 直接打回 1
}

两个 if 是并列的，而 change 和 lost 完全可能在同一次 flush 里同时为真—— 发送缓冲里有几十个包，一个触发了快重传，另一个刚好超时，这在丢包时太常见了。

原版这么写没出大问题，因为 lost 分支是无条件覆盖赋值（cwnd = 1）， 写第二遍还是 1。但换成 CUBIC 之后，减窗变成了基于当前值的相对运算 （乘一个系数），连续调用两次就是连乘——一次网络事件把窗口砍了两刀。

现场表现

丢包时吞吐塌得比预期深得多，而且恢复慢一倍。日志上看不出异常， 因为每一步都"按算法执行了"。这类 bug 的特征是：不崩溃、不报错， 只是性能不对，而性能不对很容易被归咎于网络本身。

修法是把它改成互斥的，并且明确谁优先：

/*
 * CUBIC owns both ssthresh and cwnd on loss. Only one reduction may be
 * applied per flush even when a fast retransmit and an RTO are both
 * flagged, otherwise the window is halved twice for a single event and
 * the flow takes far longer to recover than the algorithm intends.
 * RTO is the more severe signal, so it wins.
 */
if (lost) {
    ikcp_cong_cubic_on_loss(kcp, 1);       // 超时：更严重，优先
} else if (change) {
    ikcp_cong_cubic_on_loss(kcp, 0);       // 快重传：较轻
}

可以带走的一般结论：把"幂等的覆盖赋值"换成"相对运算"时， 所有调用它的地方都要重新检查调用次数。 原来写两遍无所谓的代码，改完之后写两遍就是错的。 这类回归在重构里非常隐蔽，因为改动点和出问题的点看起来毫无关系。

附：四个参数怎么调

KCP 的调优基本就是 ikcp_nodelay() 这一个函数的四个参数：

参数含义实时流建议影响
nodelay极速模式1 最小 RTO 100ms → 30ms，退避从 2 倍降到 1.5 倍
interval内部时钟间隔10 ms 决定 flush 频率，也是 RTO 的下限项之一。默认 100ms 对实时流太粗
resend快重传阈值2 被跳过几次就补发。设 0 关闭快重传，只剩超时兜底
nc关闭拥塞控制谨慎 只在链路完全可控时开，公网上开这个是把风险转嫁给别人

interval 有个隐藏影响容易被漏掉：它参与 RTO 计算 （rto = srtt + max(interval, 4*rttval)）。 也就是说调大 interval 会连带把 RTO 抬高， 在低延迟链路上尤其明显——RTT 只有 10ms 的时候，interval=100 会让 RTO 被 interval 主导。

值得记住的三句话

  1. KCP 不是"更快的 TCP"，是"用带宽换延迟的 TCP"。 选它之前先确认你的场景真的愿意付这个代价，以及链路是不是你独占的。
  2. 拥塞窗口的增长速度，决定了流的头几秒体验。 稳态吞吐是所有人都会测的指标，开流瞬间的表现却经常没人量——而用户恰恰在那一刻做判断。
  3. 给三方库做扩展，用钩子 + NULL 回退 + 共享分配器。 这三条让你的改动能在上游升级后活下来，也让扩展失败时系统能降级而不是倒下。
